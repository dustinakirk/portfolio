# 2.6 Feedback on Results & Rating Controls

Lightweight, contextual mechanisms for reacting to AI outputs—so the system can continuously learn from real usage and recover quickly when it gets things wrong.

*Last updated December 2025*

---

## Overview

Feedback and rating controls are small, always-available affordances attached to AI-generated outputs that allow users to quickly signal whether a result was helpful, harmful, or off-target. In agentic systems, these controls are essential for closing the loop between output quality, user expectations, and system learning.

This pattern appears wherever an AI agent produces a perceivable outcome: chat responses, generated documents, completed workflows, analysis summaries, or code changes. The core idea is to capture feedback in the moment of evaluation, tie it to the exact context in which it occurred, and—where appropriate—respond with immediate corrective behavior.

A well-designed feedback pattern:

* Makes it effortless to express positive or negative reactions.
* Encourages richer feedback without requiring it.
* Clarifies what the feedback will influence (personalization vs. global improvement).
* Offers inline repair for negative outcomes, not just passive collection.
* Feels respectful of user effort and interrupts the workflow as little as possible.

## Problem

Without explicit feedback mechanisms, AI-driven products often behave as opaque, static systems, even when they are technically capable of learning:

* Users have no clear way to express that an answer was wrong, incomplete, biased, or simply unhelpful.
* The system repeatedly makes the same mistakes because it does not receive structured signals about what to change or prioritize.
* Product teams cannot easily see patterns in where the agent underperforms, nor distinguish between “minor annoyance” and “critical failure.”
* Recovery from a bad response depends on the user knowing how to restate or re-prompt, which places the burden of correction on the person rather than the system.
* Trust erodes when users perceive that feedback—when offered—disappears into a void without visible impact.

Feedback and rating controls address this by making evaluation an explicit, low-friction part of the interaction loop, while also providing hooks for learning, personalization, and operational improvement.

---

## When to Use This Pattern

* When an AI agent produces **non-trivial outputs** that require judgment: strategy recommendations, forecasts, summaries, generated content, code, or configuration changes.
* When an experience involves **subjective quality** dimensions such as tone, level of detail, format, or domain-specific nuance.
* When the system offers **automation or actions with risk**, such as changing settings, sending communications, modifying data, or initiating workflows on behalf of the user.
* When a product team intends to use **real-world feedback signals** to improve models, prompts, safety filters, or user-level preferences over time.
* When support teams or administrators need **visibility into where the AI struggles**, e.g., to prioritize training data, guardrails, or product improvements.

## Probably Overkill When...

* The AI surface provides **very small, low-stakes outputs** that are easily ignored or corrected with a single click (e.g., micro-copy suggestions in a non-critical context).
* The interaction is **purely informational and obviously correct**, such as static documentation search with clear sources and simple answers.
* The system already collects **robust, task-level success metrics** (e.g., form completion, error rate) that reliably capture outcome quality without subjective rating.
* The AI functionality is **experimental, internal-only**, and feedback is being gathered via direct research sessions or structured surveys instead.

## Pattern Anatomy

Feedback on Results & Rating Controls is centered around a **feedback unit**: a consistent, compact UI attached to an AI output that captures reaction, optional detail, and scope, and may trigger immediate corrective behavior.

### Entry Points

* **Inline on AI messages or result blocks**
  For chat-based agents, a small reaction bar (e.g., 👍 / 👎) at the bottom of each assistant message, or on key “milestone” messages such as final answers or summaries.

* **At the output artifact level**
  For generated reports, documents, dashboards, or code changes, rating controls at the top-right or footer of the artifact pane: e.g., “Rate this draft” with thumbs or stars.

* **After task completion or workflow runs**
  In run logs, job history, or a completion toast for long-running jobs: e.g., “How was this result?” with quick reactions.

* **Within history or audit views**
  In conversation history, run timelines, or admin consoles, allowing retroactive rating of previous outputs, especially in B2B contexts where review may happen after the fact.

### Core Item / Object

The main repeated unit is the **feedback event**, tied to a specific AI output.

Each feedback event typically consists of:

* **Label / affordance**

  * A concise action or hover label such as “Rate response” or “Was this helpful?”
  * Iconography for fast recognition: thumbs up/down as a default, with tooltips for clarity (“Helpful” / “Not helpful”).

* **Primary control(s)**

  * **Minimum**: binary controls (👍 / 👎).
  * **Optional**: a richer scale (0–5 stars, emoji scale, or “Very helpful → Very unhelpful”) for longer or higher-stakes tasks.

* **Secondary detail controls (on click)**

  * Post-rating sheet, popover, or inline expander with:

    * Tag chips (multi-select): examples include “Too long,” “Too vague,” “Incorrect data,” “Missed instructions,” “Wrong tone,” “Out of date,” “Wrong tool or source,” “Excellent example,” “Exactly what was needed.”
    * Optional free-text field: short, single-line or small multiline input such as “What worked or did not work?” (limited length to prevent form fatigue).
  * Clear dismiss/skip actions so feedback does not block task progress.

* **Scope & persistence options**

  * Contextual messaging: e.g., “This helps improve responses in this workspace” or “This trains preferences for this project.”
  * In advanced setups, a simple toggle: “Treat this as a preference for future tasks” vs. “Apply only to this conversation.”

* **Optional metadata & status**

  * Indication that feedback was received: subtle “Feedback recorded” toast or microtext.
  * Visible state of the rating (e.g., highlighted icon) so users can see that their reaction is stored.
  * Optional visibility for admins or team leads: tags showing severity (“Critical issue,” “Minor issue”) for triage.

### Behavior & Lifecycle

1. **Initial system behavior**

   * Feedback controls appear in a neutral, subtle state near AI outputs without demanding attention.
   * For first-time users, a minimal hint or tooltip may briefly explain the purpose of the controls.

2. **User reacts to an output**

   * A quick click on thumbs up/down or a star scale captures a **reaction snapshot** with no extra friction.
   * The rating is immediately reflected in the UI (e.g., filled icon) and stored with the associated output, prompt, and context.

3. **Optional enrichment of feedback**

   * After the primary reaction, a small, non-blocking popover or sheet appears.
   * For positive feedback, tags might capture what was good: “Clear reasoning,” “Great examples,” “Helpful formatting.”
   * For negative feedback, tags focus on failure modes: “Incorrect,” “Missed constraints,” “Too long,” “Too generic,” “Unsafe or biased.”
   * Free-text input is optional and short; closing the popover does not discard the initial rating.

4. **Inline repair (for negative feedback)**

   * For thumbs down, the system offers **quick repair options** aligned with common tags:

     * “Regenerate with: [More concise] [More detailed] [Different tone] [Narrower scope] [Focus on X constraint]”
   * Selecting an option triggers:

     * A visible acknowledgment by the agent (e.g., “Understood, re-focusing on profitability targets.”).
     * A new output that makes the change explicit (e.g., highlighting the applied constraint in the regenerated result).
   * Where appropriate, the system may surface a chip: “Remember this preference for similar tasks?” to integrate with Teach Me Interfaces (Pattern 2.4).

5. **Preference learning & scope application**

   * Repeated patterns of feedback (e.g., frequent “Too long” on summaries) can be automatically promoted into persistent preferences:

     * Example: “Summaries are now defaulted to bullet points and <N> sentences in this workspace.”
   * Clear copy communicates when such a preference has been adopted and where it applies (project, workspace, global account).

6. **Logging & aggregation**

   * Every feedback event is logged with:

     * Session or conversation ID.
     * User role or segment (e.g., analyst, manager, admin).
     * Output type (chat answer, report, run, code suggestion, etc.).
     * Tags and optional text.
   * Product teams and admins can access aggregated views:

     * Low-rating hotspots by task type, feature area, or integration.
     * Temporal trends (e.g., improvements after a prompt or model update).
     * Top recurring complaints and praises.

7. **Follow-up and escalation (B2B-heavy scenarios)**

   * Some negative feedback (e.g., “Unsafe,” “Compliance issue,” “Data leak risk”) may trigger:

     * Automatic routing into a moderation queue.
     * Alerts for security, compliance, or product operations.
   * Epic-level issues arising from patterns of feedback can guide roadmap decisions and model interventions.

## Content & Microcopy Guidelines

* **Orient toward helpfulness, not blame**

  * Use neutral labels such as “Helpful / Not helpful” rather than “Good / Bad,” to frame feedback as collaborative improvement.

* **Clarify impact**

  * Short, contextual descriptions such as “Helps improve future responses in this workspace” prevent unrealistic expectations about immediate or global changes.

* **Invite, do not coerce**

  * Avoid gating actions or content behind mandatory ratings.
  * Feedback prompts should be easy to ignore or dismiss without penalty.

* **Acknowledge effort**

  * Brief confirmations (“Feedback recorded”) reassure users that feedback matters, without requiring long explanations.

* **Be specific where the system can act**

  * Offer options that map directly to system capabilities: “Shorter,” “More formal,” “Cite sources,” “Focus on [field],” rather than vague options the system cannot interpret.

## Personalization, Learning, and Scope

A strong rating pattern differentiates between:

1. **Contextual correction**

   * The system uses feedback to immediately improve **the current output** or subsequent turns within the same task or conversation.
   * Example: A “Too long” tag on a summary drives shorter re-generation in the same thread.

2. **Preference learning**

   * Frequent feedback signals are elevated into persistent preferences:

     * Level of detail (summary vs. deep dive).
     * Preferred format (bullets vs. narrative vs. table).
     * Tone (formal vs. casual vs. technical).
   * These preferences can be surfaced and edited via Teach Me Interfaces (Pattern 2.4).

3. **Global product learning**

   * Aggregated feedback across tenants helps improve prompts, retrieval strategies, integration defaults, or guardrails.
   * For regulated or sensitive environments, training on user text may require explicit consent and configuration.

Key considerations:

* **Explicit vs. inferred preferences**

  * When inferred from feedback, preferences should be confirmed before major behavioral changes occur.

* **Multi-tenant boundaries**

  * In B2B software, tenant-specific learning should respect data boundaries, role-based access, and contractual terms.

* **Role-aware behavior**

  * Feedback from different roles (e.g., engineers, legal reviewers, executives) may need different weights or routing paths.

## Data & Instrumentation Considerations

To make this pattern operationally valuable:

* **Track core metrics**

  * Feedback coverage: percentage of AI outputs that receive ratings.
  * Rating balance: distribution of positive vs. negative reactions.
  * Tag frequencies: most common failure modes and strengths.
  * Repair effectiveness: improvement in ratings after automatic re-generation.

* **Link to outcomes**

  * Correlate feedback with downstream metrics:

    * Task completion vs. abandonment.
    * Manual corrections vs. acceptance of AI-generated changes.
    * Support tickets or escalations originating from AI outputs.

* **Detect anomalies**

  * Sudden spikes in negative feedback for a feature, segment, or time window can flag regressions in model performance, prompts, or data pipelines.

* **Respect privacy and compliance**

  * Clearly document whether free-text feedback may be used for model training, and provide options to restrict sensitive content from training pipelines.

## Accessibility & Inclusivity

* **Keyboard and screen reader support**

  * Rating controls must be fully operable via keyboard with clear focus states.
  * Icons must have accessible names: e.g., “Mark response as helpful” instead of “Thumbs up.”

* **Touch-friendly targets**

  * Controls should meet minimum target size guidelines to avoid mis-taps, especially on smaller screens.

* **Color-independent signaling**

  * Use more than color to indicate state (filled icons, underlines, or labels) to ensure clarity for color-blind users.

* **Language and cultural sensitivity**

  * Avoid idioms in labels and tags; prefer simple, literal language that localizes well.
  * Emoji-based scales, if used, should be carefully tested for cultural interpretation.

---

## Error States & Edge Cases

* **Streaming outputs**

  * For streaming answers, rating controls become active once the message is complete, not during generation, to avoid rating incomplete content.

* **Partial or failed runs**

  * When a task fails or times out, a focused feedback component can capture failure-specific data: “Error occurred,” “Stuck,” “Took too long.”

* **Undo / update rating**

  * Users may change their rating if they later reassess an output; the UI should support toggling or re-rating.

* **Archived or deleted content**

  * Feedback should persist in logs even if the original content is archived, with appropriate redaction or truncation for privacy.

* **No-learning environments**

  * In environments where learning is disabled, feedback can still route to admins or product teams, but microcopy must not imply real-time personalization.

---

## Anti-Patterns to Avoid

* **Mandatory feedback dialogs**

  * Blocking the workflow with “Rate this before continuing” dialogs creates frustration and reduces trust.

* **Overly complex forms**

  * Long surveys or multi-step forms after each interaction discourage honest feedback and reduce participation.

* **Ambiguous icons without labels**

  * Using only icons (e.g., faces, stars) without text or tooltips can lead to misinterpretation of meaning.

* **Ignoring negative feedback**

  * If negative ratings have no visible effect (no acknowledgment, no repair, no change over time), the pattern becomes performative and erodes trust.

* **Overfitting to vocal minorities**

  * Overreacting to a small number of ratings from a non-representative group can degrade the experience for others; aggregation and segmentation are essential.

* **Blurring scope boundaries**

  * Suggesting that a single rating will “fix the model” or “improve all responses everywhere” creates unrealistic expectations and potential legal risk.

## Example Scenarios

1. **Strategy co-pilot in a B2B analytics platform**

   * The agent generates a quarterly business narrative.
   * The business analyst gives a thumbs down, selects “Missed constraints,” and enters “Ignored profitability targets.”
   * The agent acknowledges the constraint, regenerates the narrative with profitability clearly highlighted, and offers to remember “profitability targets as non-negotiable” for planning tasks in this workspace.

2. **Sales assistant drafting outbound emails in a CRM**

   * A sales rep receives an AI-generated email draft and marks it as “Not helpful” with the “Too formal” tag.
   * The assistant regenerates with a more conversational tone and proposes setting “Conversational tone” as a default preference for that rep’s outbound communications.

3. **Code assistant in a developer platform**

   * A developer rates a code suggestion with a thumbs down and tags “Incorrect logic” and “Security concern.”
   * The feedback routes to a higher-priority review bucket, and the assistant immediately regenerates with safer patterns and explicit reasoning about the change.

4. **Customer-facing support bot in B2C web app**

   * A customer marks a bot answer as “Not helpful” and selects “Did not resolve my issue.”
   * The system follows up with: “Would a human agent be more helpful?” and escalates the conversation with the transcript and rating attached.

## Implementation Checklist

* [ ] Place feedback controls consistently near AI outputs (messages, documents, run results) without obstructing main actions.
* [ ] Provide a minimal, always-available primary reaction control (e.g., thumbs up/down) for quick evaluation.
* [ ] On reaction, open a small, non-blocking interface for tags and optional text; do not make it mandatory.
* [ ] Offer inline repair options after negative feedback that map to specific, controllable changes (length, tone, scope, constraints).
* [ ] Clearly communicate what feedback will influence (current response, future preferences, product improvement) and at what scope.
* [ ] Log feedback with rich context (task type, role, tags, timestamps) and expose aggregate insights to product and operations teams.
* [ ] Implement accessibility best practices for icons, labels, keyboard navigation, and screen readers.
* [ ] Provide safe handling and routing for sensitive tags (e.g., “Unsafe,” “Bias,” “Security risk”) with escalation paths where required.
* [ ] Support editing or undoing feedback to reflect changes in judgment.
* [ ] Regularly review feedback data and close the loop by improving models, prompts, UX flows, and help content—and by removing or refining tags that are rarely used or confusing.
