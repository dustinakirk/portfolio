# 2.3 Progressive Disclosure Modes

A structured mode system that reveals complexity gradually, supporting both novices and experts while maintaining trust in agentic AI behavior.

*Last updated December 2025*

---

## Overview

Progressive Disclosure Modes introduce distinct interaction levels (for example, “Simple” and “Advanced / Developer / Supervisor”) that align the AI experience with the needs, skills, and risk-tolerance of different user groups. Rather than presenting every detail of prompts, tools, logs, and configuration at once, the interface reveals only what is necessary at each level of expertise.

This pattern frequently appears around agentic AI surfaces such as orchestration canvases, automation builders, AI copilots, and workflow designers in both B2B and B2C web applications. In these contexts, it transforms a single overwhelming interface into a layered one, where non-expert roles can work safely and confidently while expert roles retain full visibility, control, and debuggability.

## Problem

Agentic AI systems often generate complex, multi-step behavior that can feel opaque or overwhelming, especially when multiple tools, data sources, and agents are involved. A single flat interface rarely works for all stakeholders.

Without Progressive Disclosure Modes:

* Non-technical users encounter a dense surface full of prompts, graphs, tokens, and tool payloads, creating confusion, anxiety, and avoidance.
* Expert users lack sufficient visibility into what the AI is actually doing, making it difficult to debug failures, assure safety, or explain outcomes to stakeholders.
* Shared workspaces become contested, with competing demands for “simpler” vs “more detailed” interfaces, leading to inconsistent, ad-hoc views and workarounds.

The pattern is needed to balance clarity for novices with transparency and control for experts, without fragmenting the product into separate, siloed tools.

---

## When to Use This Pattern

* AI orchestration or automation builders where a single workflow must serve product managers, analysts, engineers, operations, and compliance roles.
* Multi-agent or tool-using AI systems where the underlying behavior (tool calls, retries, fallbacks, loops) is significantly more complex than the surface task description.
* High-stakes or regulated environments (for example, finance, healthcare, infrastructure, enterprise data platforms) where detailed auditability and oversight are required.
* AI copilots embedded in existing enterprise applications where different personas (for example, frontline employees vs system administrators) perform very different tasks using the same assistant.
* Scenarios where advanced configuration (prompts, parameters, routing rules, safeguards) must be available to a subset of expert maintainers while the broader audience interacts with a simpler abstraction.

## Probably Overkill When...

* Single-step, low-risk tasks where AI suggestions are narrow and reversible (for example, rewriting a sentence in a text field).
* Small, single-person tools with limited complexity and no meaningful distinction between novice and expert roles.
* Internal prototypes or experiments where the primary goal is speed of iteration rather than long-term maintainability or trust at scale.
* Cases where the “advanced” view adds little beyond cosmetic detail, and the underlying behavior is already fully understandable from the default UI.

## Pattern Anatomy

Progressive Disclosure Modes typically manifest as a mode toggle connected to an expanded system view. The pattern adds a layer of state above the individual components, changing what is visible, editable, and emphasized based on the selected mode.

### Entry Points

* **Primary entry point – Global mode switch:**
  A labeled toggle (for example, “Simple / Supervisor Mode”) in a consistent location around the main agentic surface, such as the canvas header, assistant sidebar header, or workflow builder toolbar.

* **Secondary entry point – Local “Show details” controls:**
  Inline affordances such as “Show underlying prompt,” “Expand run details,” or “View execution trace” that temporarily reveal advanced information without permanently changing global mode.

* **Contextual entry point – Settings or role configuration:**
  Workspace- or organization-level preferences in settings where administrators can define defaults per role (for example, product managers default to Simple Mode, engineers to Supervisor Mode) and restrict access to certain modes if needed.

### Core Item / Object

The core object in this pattern is the **Mode Configuration**, which represents a named view of the same underlying agentic system.

Typical structure:

* **Label:**

  * Simple, role-anchored names such as “Simple,” “Guided,” “Business View” vs “Advanced,” “Developer,” “Supervisor,” or “Trace View.”
  * Labels communicate **who** the mode is for and **what kind of control** it enables (for example, “Recommended view for most teammates” vs “Full system trace for debugging and oversight”).

* **Description / Statement:**

  * A short explanation that clarifies scope:

    * Simple mode: “Shows key steps and outcomes with plain-language explanations.”
    * Advanced mode: “Exposes prompts, variables, tools, logs, and execution trace for debugging and governance.”

* **Controls:**

  * Primary toggle or segmented control to switch modes.
  * Optional inline action to “Remember this for this workspace” to persist preferences.
  * Inline “Learn more” or help link to explain what changes when switching from one mode to another.

* **Optional Metadata:**

  * Scope: whether the mode preference applies at user, project, or workspace level.
  * Role / permission requirements (for example, “Available to engineering and admin roles”).
  * Status or risk indicators (for example, “Advanced mode may expose sensitive data” or “Read-only trace view”).
  * Indicators when the current view is constrained by policy (for example, “Supervisor Mode disabled by organization policy”).

### Behavior & Lifecycle

Progressive Disclosure Modes are most effective when they behave predictably across sessions and contexts.

1. **Initial system behavior**

   * The system determines a default mode based on role, permissions, prior usage, or organizational policy.
   * The UI clearly indicates which mode is active and provides a concise explanation on first visit, often via a subtle coach mark, tooltip, or inline explainer.

2. **Discovery and education**

   * The mode switch appears close to the primary AI surface (canvas, assistant panel, builder).
   * On first encounter, a lightweight prompt explains the difference between modes and reassures non-expert users that switching to an advanced mode is optional and reversible (unless restricted by policy).

3. **Switching modes**

   * Switching between Simple and Advanced modes is fast, reversible, and visually coherent; shared elements stay in place while additional panels or details slide in or expand.
   * Simple Mode hides complex prompts, variables, and logs behind collapsed sections, focusing on tasks, outcomes, and human-readable rationales.
   * Advanced Mode reveals tool calls, prompt templates, variables, token usage, execution graphs, retries, and logs. In some implementations, Advanced Mode also unlocks editing of prompts or routing rules.

4. **Preference persistence**

   * The selected mode is persisted at **user + workspace** or **user + project** level, so individuals do not have to reconfigure the interface every session.
   * If an organization sets a global default per role, personal overrides are either honored or explicitly disallowed with clear messaging.

5. **Task execution and monitoring**

   * During agentic runs, Simple Mode emphasizes progress and outcomes (“Research done,” “Draft generated,” “Review completed”), with optional “peek” affordances to see more detail.
   * Advanced Mode provides a live trace or timeline: each tool call, prompt, and decision appears with status, timing, and any errors, supporting debugging, experimentation, and audits.

6. **Escalation and safety interventions**

   * Before high-impact actions (for example, sending emails to customers, modifying production data, triggering deployments), the system may temporarily surface a “More details” or “Review underlying actions” panel even in Simple Mode, giving access to an advanced preview or confirmation step.
   * In regulated or high-risk contexts, certain workflows may **require** Advanced or Supervisor Mode for final approval, enforced by permissions.

7. **Error handling and troubleshooting**

   * In Simple Mode, failures are described in human-readable terms with a clear next step (retry, adjust input, or escalate).
   * Advanced Mode reveals stack traces, raw tool responses, prompt content, and intermediate states, supporting issue resolution without resorting to external debugging tools.

8. **Long-term evolution and governance**

   * As the system evolves, the set of visible elements in each mode can be updated, but the meaning of each mode (who it serves and what it exposes) remains stable.
   * Telemetry on mode usage, toggling frequency, and task outcomes informs refinements to defaults, copy, and access policies.

## Implementation Notes for Agentic AI Systems

### Mode Design and Labeling

* Align mode names with roles and mental models rather than technical jargon alone. For example, “Business View” vs “Technical View” often resonates better than purely “Basic” vs “Advanced.”
* Avoid implying that Simple Mode is inferior; instead, position it as the recommended, safer, or more focused view for most workflows.
* Make the scope of the mode explicit: modes affect **what is shown**, not the underlying correctness or safety guarantees of the AI system.

### What Each Mode Typically Shows

**Simple / Guided Mode**

* High-level task description and natural language steps (for example, “Research competitors,” “Draft email,” “Summarize findings”).
* Key inputs and outputs only (user input, main AI response, critical parameters the user selected).
* Plain-language explanations of what the agent is about to do or has done.
* Minimal, human-centric controls (approve, edit, retry, discard), with advanced toggles collapsed or hidden.
* Limited technical metrics (for example, “Run time,” “Success / failed”) without tokens, latency charts, or log streams.

**Advanced / Developer / Supervisor Mode**

* Full or partial visibility into:

  * Prompt templates, system messages, and dynamic variables.
  * Tool calls and responses, including payloads and error messages, subject to data sensitivity policies.
  * Execution graph or timeline of agent steps, including retries, branching, and fallbacks.
  * Parameter controls (temperature, model choice, routing thresholds) as appropriate for the product.
  * Token usage, latency per step, and other performance metrics.
* Additional capabilities:

  * Editing prompts or configuration.
  * Saving, versioning, or comparing different runs.
  * Exporting traces or logs for external analysis.

### Role- and Policy-Aware Behavior

* Integrate mode access with role-based access control:

  * Some roles may never see Advanced Mode, or may see it in read-only form.
  * Supervisor Mode can be restricted to administrators, engineers, or governance teams for high-risk workflows.
* Surface policy-driven limitations clearly:

  * For example: “Execution traces are redacted in this workspace due to data policies” or “Prompt editing is disabled for production workflows.”

### State Management & Persistence

* Persist mode selection at both:

  * **User level**: personal preference and working style.
  * **Workspace or project level**: context-specific defaults, especially in multi-tenant B2B products.
* Ensure that switching workspaces or projects updates the mode appropriately rather than applying a single global preference that may not match local policies.

## Example Use Cases

### Multi-Agent Orchestration Canvas (B2B SaaS)

* Product managers interact with a high-level canvas showing three nodes: “Research → Draft → Review,” each with a plain-language description and example inputs/outputs.
* The canvas header includes a segmented control: “Business View | Supervisor Mode.”
* In Business View, clicking “Run Flow” shows progress and a final summary; details are tucked behind “View details” drawers.
* When a technical stakeholder selects Supervisor Mode, the same canvas expands to show:

  * Individual tools (search API, document retriever, LLM, reviewer agent).
  * Prompt templates for each node.
  * Logs and traces of each run, including errors and retries.

### Embedded AI Copilot in CRM

* Sales representatives see a simple assistant panel that summarizes accounts, drafts emails, and prepares meeting notes. Observed behavior is expressed in practical terms with minimal configuration.
* A “Technical View” toggle appears for administrators and operations teams, revealing:

  * Which data sources the assistant used for a given summary.
  * The underlying prompts and filters.
  * Monitoring information such as rate limits, latency, and failure reasons.

### AI-Powered Data Transformation Tool

* Analysts create transformations with a natural-language interface and preview outputs in Simple Mode.
* Data engineers switch to Advanced Mode to:

  * Inspect generated SQL or code.
  * Review execution plans and performance statistics.
  * Validate that queries respect privacy and compliance constraints before enabling production pipelines.

## Anti-Patterns and Pitfalls

* **Mode proliferation:** Introducing three or more overlapping modes (“Simple,” “Advanced,” “Expert,” “Debug,” etc.) without clear distinctions, leading to confusion and misconfiguration.
* **Hidden responsibilities:** Burying critical safety or approval responsibilities only in Advanced Mode, while non-expert roles trigger high-impact actions without sufficient context.
* **Copy that shames users:** Labeling modes in ways that make non-expert users feel incompetent (“Beginner Mode,” “Dumb Mode”), eroding trust and adoption.
* **Inconsistent application:** Implementing the mode toggle on one screen but not on related workflows, causing the same user to see different abstractions in different parts of the product.
* **Leaking sensitive data:** Exposing raw tool payloads, prompts, or logs containing PII or confidential information in Advanced Mode without safeguards, contradicting trust and legal requirements.

---

## Content & Microcopy Guidelines

* Clearly state **who** each mode is for and **what changes** when switching, in one short sentence each.
* Emphasize safety and focus in Simple Mode (for example, “Recommended view for most teams; focuses on tasks and outcomes”).
* Emphasize transparency and control in Advanced/Supervisor Mode (for example, “Shows full system trace, configuration, and logs for debugging and oversight”).
* Use consistent naming across UI surfaces, documentation, and training materials so that “Supervisor Mode” always means the same set of capabilities.

---

## Instrumentation & Success Metrics

To evaluate and refine Progressive Disclosure Modes:

* Track **mode adoption** by role, workspace, and feature area.
* Monitor **toggle frequency** within sessions; frequent switching may indicate poor defaults or unclear distinctions.
* Compare **task success, completion time, and error rates** between modes, segmented by role.
* Observe **support tickets and qualitative feedback** as modes roll out; confusion about what each mode does often surfaces early.
* Measure **usage of advanced artifacts** (traces, logs, prompt editors) to prioritize which expert features are most valuable.
