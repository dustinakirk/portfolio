# 3.1 Kill Switch, Pause & Resume

A control pattern that gives users immediate, graduated control over long‑running or autonomous AI agents through clear Pause, Resume, and Stop mechanisms.

*Last updated December 2025*

---

## Overview

Agentic AI systems increasingly run long‑lived, multi‑step workflows that reach into production systems, developer tools, financial accounts, and third‑party APIs. This pattern introduces a dedicated set of controls—Pause, Resume/Continue, and Stop/Cancel—so that users can confidently start powerful automations knowing they can always slow, adjust, or terminate execution.

In a typical web application, this pattern appears in or near an AI agent’s chat interface, task detail view, or run history. It anchors trust by making control *visible, persistent, and reversible* rather than implicit or hidden behind technical tools or administrator actions.

> **Example placeholder**: Interactive mock where an AI “Data Hygiene Agent” is cleaning CRM records. The UI shows a step list with progress, plus a fixed control strip with “Pause”, “Resume”, and “Stop”. When “Pause” is triggered, the agent finishes the current step, switches to a “Paused at step 3 of 8” state, shows a summary of completed work, and allows editing of the remaining plan before “Resume”.

---

## Problem

Without explicit kill, pause, and resume controls, long‑running or autonomous agents create several trust and safety issues:

* **Loss of perceived control**
  When an agent keeps taking actions (sending emails, changing records, modifying configs) without a clear way to intervene, users feel locked out of their own systems and hesitate to delegate important work.

* **Fear of runaway damage and cost**
  A misconfigured prompt, wrong environment, or mis‑scoped task can lead to large‑scale destructive changes, data exposure, or unbounded spend if there is no reliable way to halt execution.

* **Inability to inspect and correct mid‑execution**
  Binary “run or don’t run” workflows force users to choose between over‑trusting the agent or aborting entirely. Without a pause‑and‑inspect option, teams cannot safely “ride along” and adjust plans as reality unfolds.

* **Operational risk and regulatory concerns**
  Compliance, security, and operations teams need provable mechanisms to immediately stop or quarantine agent activity in case of incident, misalignment, or misuse, not just polite requests to the model.

A well‑designed kill switch and pause/resume pattern addresses these concerns by treating control as a first‑class feature, not an afterthought.

---

## When to Use This Pattern

Use this pattern whenever an AI agent:

* **Executes multi‑step or long‑running workflows**
  Examples: code refactoring across many files, multi‑stage data pipelines, campaign creation and launch, incident remediation, or bulk record updates.

* **Has side effects on critical systems or data**
  Examples: production APIs, payment systems, HR or legal data, infrastructure, security policies, customer communications.

* **Runs asynchronously or in the background**
  Examples: scheduled or recurring automations, “fire‑and‑forget” jobs, agents that continue acting after the user leaves the page or logs out.

* **Acts with partial autonomy**
  Examples: agents allowed to create tasks, call tools, or chain actions without step‑by‑step approvals.

---

## Probably Overkill When...

This pattern can be simplified or omitted when the agent:

* **Only provides short, stateless responses**
  Simple Q&A, short completions, or “suggested reply” generation that does not call tools or modify systems.

* **Operates in a read‑only sandbox with no persistent effects**
  View‑only analysis or summarization over non‑sensitive data, where risk and cost are low.

* **Completes in well under a second**
  Single, atomic actions with trivial impact where a browser refresh or “Stop generating” streaming control already provides adequate interruption.

In these cases, a lightweight “Stop generating” control or natural latency may be sufficient.

## Pattern Anatomy

The Kill Switch, Pause & Resume pattern centers on a visible control cluster associated with a specific agent *run* or *session*, backed by robust state handling and auditability.

### Entry Points

* **Primary entry point – Agent surface**
  A persistent control strip near the chat input, plan header, or run status bar within the agent’s main workspace. This is where most users expect control and where any running task should be clearly indicated.

* **Secondary entry point – Run or job list**
  List views of current and historical runs (e.g., “Active automations”, “Recent jobs”) with inline controls to Pause or Stop individual runs without opening their full detail view.

* **Contextual entry point – Notifications and banners**
  Toasts, banners, or in‑product notifications that appear when an agent starts or continues work, each with inline Pause/Stop actions (for example, “Data hygiene agent is updating 2,341 records – [Pause] [Stop]”).

### Core Item / Object

The primary object in this pattern is the **Agent Run** (sometimes called a job, workflow, or session):

* **Label**
  Human‑readable, specific description such as:
  “Refactor API module”, “Clean up CRM duplicates – Run #12”, or “Rotate expired access keys (Production)”.

* **Description / statement**
  A short explanation of what the agent is doing and how far along it is, often derived from its initial plan.
  Example: “Step 3 of 7 – Updating 123 customer records in ‘Enterprise’ segment” or “Scanned 48/120 repositories; triaging security findings next.”

* **Controls**
  Inline controls, consistently ordered and labeled, commonly including:

  * **Pause** – Graceful halt after the current atomic step; preserves state and plan.
  * **Resume / Continue** – Continue from the last checkpoint after a Pause.
  * **Stop / Cancel** – Terminate the run, stop tool calls, and finalize a partial or rolled‑back state.
  * Optional: **Undo last batch**, **Open diff**, **Run in sandbox**, **Promote to production**.

* **Optional metadata**
  Additional context that supports trust and governance, such as:

  * Start time, elapsed time, and estimated time remaining
  * Environment (sandbox, staging, production)
  * Initiator (person, team, or system trigger)
  * Scope (e.g., affected projects, record counts, services)
  * Cost so far and configured limits
  * Run ID or link for audit / observability tools
  * Risk level or approval status (e.g., “Pre‑approved playbook” vs “Experimental agent”)

## Behavior & Lifecycle

### 1. Pre‑Run: Plan and Arming the Controls

1. The agent proposes a plan or receives a command that implies multi‑step work.
2. The UI presents a summary of the plan, scope, and environment, with the control cluster visible but initially disabled except for **Start**.
3. When the run is initiated, the system also “arms” the Pause/Stop controls for this run and ensures the backend provides real‑time status and checkpoints.

Key design points:

* Controls must be visible *before* the agent begins acting so users understand how they will retain control once the run starts.
* For high‑risk runs, a confirmation step can show affected scope, environment, and configured cost/impact limits before allowing execution.

### 2. Running: Active Execution with Live Controls

While the agent is running:

* Status indicators show a **Running** state with activity signals (progress bar, step list, streaming logs, or at least a spinner with textual status).
* The **Pause** and **Stop** buttons become prominent, clearly enabled, and remain visible as the user scrolls (for example, through a sticky header or floating control).
* A brief textual indicator explains what is currently happening, not just that something is happening (“Applying config to service `checkout-api`”, not “Working…”).

Behavioral expectations:

* The system treats pause/stop commands as high‑priority control signals, not suggestions.
* A pause/stop request is acknowledged immediately in the UI (e.g., “Pausing after current step…”) even if the underlying work needs time to reach a safe checkpoint.

### 3. Pause: Graceful Interruption and Inspection

When **Pause** is triggered:

1. The agent finishes the current atomic operation (for example, updating the current batch of records, finishing a file write, or exiting the current tool call).
2. No new steps or tool calls are started.
3. The run transitions through a short **Pausing…** state into **Paused**.

In the **Paused** state:

* The UI clearly indicates “Paused by <actor> at <time>” (for example, “Paused by Security Team at 14:32 UTC”).
* A snapshot summary is shown:

  * Steps completed vs planned
  * Key changes already applied
  * What is planned next
  * Any relevant metrics (time, cost, resource usage)
* The plan and parameters for remaining steps may be editable, depending on the agent design:

  * Adjust remaining scope (e.g., limit to sandbox, smaller subset of records, one project instead of many).
  * Change execution options (e.g., “require approval for each remaining step” or “switch to dry‑run mode”).
  * Add clarifying instructions or constraints via chat.

Controls in Paused state typically include:

* **Resume** (primary)
* **Stop** (secondary but still visible)
* Optional: “Apply only completed changes”, “Export diff”, or “Clone run as draft”.

### 4. Resume: Continue From Checkpoint

When **Resume / Continue** is triggered:

1. The system revalidates any edited plan parameters and environment (for example, confirms that production access is still permitted and cost limits have not been exceeded).
2. A brief confirmation may appear for high‑risk changes summarizing: “Continue from step 4 of 7, limited to <scope>.”
3. The run transitions to **Resuming…** and then back to **Running**, picking up from the last checkpoint.

Key expectations:

* Resume should not re‑execute previously completed steps unless explicitly requested (for example, in a “rerun from beginning” action).
* Any differences between the original and updated plan should be logged and clearly visible in the audit trail.

### 5. Stop / Cancel: Termination and Recovery

When **Stop / Cancel** is triggered:

1. The system stops initiating new steps immediately and attempts to interrupt any in‑flight tool calls at the nearest safe boundary.
2. The run transitions through **Stopping…** to **Stopped** or **Canceled**, with clear ownership (e.g., “Stopped by Admin”, “Stopped by cost limit policy”).
3. The UI presents a **post‑mortem summary**, including:

   * Which steps completed successfully
   * Which steps were in progress or skipped
   * What changed in the underlying systems (e.g., “23 files updated, 4 new pull requests created, 0 changes pushed to production”)
   * Whether any rollback actions were taken or are available

Where possible, include **one‑click rollback** affordances:

* “Undo last batch (23 records)”
* “Revert this run in Git”
* “Restore previous configuration snapshot”

When fully automatic rollback is not feasible, present:

* Links to supporting tools (e.g., version history, activity logs, or incident management).
* Clear next steps for manual remediation.

### 6. Post‑Run: Logs, Audits, and Learning

After a run ends (successfully, paused indefinitely, or stopped):

* The run is accessible from a **history or runs list**, preserving:

  * Timeline of state changes (Started, Paused, Resumed, Stopped)
  * Responsible actor for each state change
  * Detailed logs or step events
  * Any alerts or policy interventions (e.g., “Stopped by cost guardrail”)
* The pattern encourages design of **reusable run configurations**:

  * “Re‑run with same parameters in sandbox”
  * “Create recurring automation based on this run, but require approval at step 3”
* Incident and analytics tools can leverage this history to improve default plans, safeguards, and thresholds over time.

## States & Status Model

A clear state model helps implementation and UX stay aligned. Common states for this pattern:

* **Not started** – Plan created, no actions taken.
* **Queued** – Waiting on capacity, approvals, or scheduling window.
* **Running** – Actively executing steps and tool calls.
* **Pausing** – Pause requested; finishing current atomic operation.
* **Paused** – Execution halted; state preserved.
* **Resuming** – Resumption requested; re‑establishing tools/context.
* **Stopping** – Stop requested; terminating active operations.
* **Stopped / Canceled** – Run terminated before completing planned steps.
* **Completed** – Finished all planned steps successfully.
* **Errored / Failed** – Stopped by errors; may be recoverable or not.
* **Rolled back** – Completed or stopped, then reverted (fully or partly).

UI guidelines:

* Use concise, unambiguous labels consistent across product surfaces.
* Display cause where relevant: “Paused by user”, “Stopped by policy”, “Stopped by system error”.
* Avoid visually confusable states (for example, Paused vs Completed) without clear textual distinction.

---

## Content & Microcopy Guidelines

Good microcopy is critical to maintaining trust and avoiding panic during interventions.

**Control labels**

* Prefer **Pause**, **Resume**, **Stop**, **Cancel**, **Undo**, and **Rollback** over bespoke verbs.
* Avoid ambiguous or overly clever labels such as “Chill”, “Nuke”, or “Freeze” in serious B2B contexts.

**Status messaging**

* Pair each state with a short, explicit description:

  * “Pausing after current batch of 500 records.”
  * “Paused at step 4 of 9: Drafted emails, not yet sent.”
  * “Stopped before applying config changes to production.”
* Distinguish between **system‑initiated** and **human‑initiated** actions (“Stopped by fraud detection policy” vs “Stopped by Marketing Team”).

**Confirmation dialogs**

* For Stop/Cancel, focus on consequences:

  * Scope of completed changes
  * Whether rollback is available
  * Impact of stopping now (e.g., “Some drafts will remain unsent.”)
* For Resume after edits, summarize deltas:

  * “Continuing with reduced scope: only accounts in region ‘EMEA’.”

**Post‑run summaries**

* Present a balanced picture: “Done”, “Not done yet”, and “Not attempted” sections.
* Highlight reversible vs irreversible changes.

## Interaction & Visual Design

* **Persistent controls**
  Keep Pause/Stop visible while the agent is active, even when the user scrolls through long logs or diff views (e.g., dock controls in a sticky footer or header).

* **Hierarchy and emphasis**

  * When running, emphasize **Pause** and **Stop**.
  * When paused, emphasize **Resume**; keep **Stop** available but secondary.
  * When stopped or completed, demote controls and emphasize logs/rollback actions.

* **Clear affordances for risk**

  * Use visual distinction (icon + color) for Stop/Cancel to signal higher impact.
  * Avoid overusing “danger” styling for non‑destructive actions like Pause.

* **Cross‑surface consistency**

  * The same run should show consistent state and affordances whether viewed in chat, in a dedicated run detail page, or in an admin console.
  * Admin‑level “global kill switches” should visually signal broader scope than per‑run controls.

* **Accessibility**

  * Ensure all controls are keyboard‑navigable and screen‑reader friendly.
  * Provide textual equivalents for status icons or colors (“Paused, not running” instead of relying on color alone).

## Variations & Extensions

### 1. Levels of Kill Switch

* **Local run control**
  Controls that apply only to a single run or session (typical in user‑facing agent UIs).

* **Agent‑level kill switch**
  Controls to disable an entire agent (e.g., “Turn off incident auto‑remediation agent”), preventing new runs but leaving existing ones to complete or pause gracefully.

* **Global / tenant kill switch**
  Emergency control in admin/governance tooling that:

  * Revokes agent credentials and tool access
  * Blocks new agent requests
  * Pauses or stops all active runs in a tenant or environment

Each level should clearly communicate scope to avoid confusion or unintended outages.

### 2. Soft vs Hard Stop

* **Soft Stop**

  * Complete the current atomic step.
  * Flush any buffered writes.
  * Transition to a stable Stopped state accompanied by clear summary.
* **Hard Stop**

  * Immediately cancel operations even if it risks leaving partial state.
  * Usually reserved for high‑severity incidents, non‑production environments, or where rollback is trivial.

Configuration options can allow administrators to choose which type is used by default and where.

### 3. Automatic vs Manual Triggers

In addition to manual user actions, the same stop mechanisms can be triggered automatically by guardrails such as:

* Spend or token limits
* Anomaly detection (error spikes, unusual patterns)
* Policy violations (data exfiltration signals, forbidden actions)
* Timeouts or SLA breaches

The UI should treat these as first‑class events (“Stopped by cost limit – $500 threshold reached”) and provide appropriate next steps.

## Error, Edge Cases & Anti‑Patterns

### Edge Cases to Handle

* **Pause requested during a long atomic operation**
  Communicate that pausing will occur after the current operation completes and show visible progress so the user does not assume the command failed.

* **Failed pause or stop**
  If the backend cannot honor the request (network issues, tool limitations), clearly state that:

  * The run is still active.
  * The system is retrying or has fallen back to a policy (e.g., “Switching to hard stop after timeout.”).

* **UI disconnect from backend state**
  When a browser tab is closed or the network drops, the agent may continue running. On reconnection:

  * Reconcile and display the authoritative state from the backend.
  * Replay relevant events so the user understands what happened while away.

* **Inconsistent state between tools**
  If some tools honor stop/pause and others do not, design for:

  * Partial completion reporting, not false “Stopped everywhere” assurances.
  * Clear tagging of which systems may still be in motion.

### Anti‑Patterns

* Hiding Pause/Stop in overflow menus during active runs.
* Implementing a “Stop generating” UI that only stops text streaming but not underlying actions.
* Clearing logs or diffs when a run is stopped, preventing audit and repair.
* Using the same styling for low‑risk and high‑impact actions, leading to accidental stops.
* Over‑relying on natural language commands (“stop”, “abort”) without reliable, dedicated controls.

## Technical & Governance Considerations

While this pattern is primarily UX, effective implementation depends on several architectural choices:

* **Atomic steps and checkpointing**

  * Design workflows as sequences of small, atomic steps that can be safely completed, paused, and resumed.
  * Persist state in durable storage (not just in model memory) so runs can be resumed after failures or restarts.

* **Structured telemetry and audit logs**

  * Capture each state change, tool call, and control action with actor, timestamp, and context.
  * Store logs in a way that supports audits, incident investigations, and analytics.

* **Credential and permission management**

  * Wire stop/kill switches into credential revocation paths (for example, API keys, OAuth tokens, ephemeral role credentials).
  * Align pause/stop behaviors with role‑based access control (RBAC) so only appropriate roles can stop or modify certain runs.

* **Guardrails integration**

  * Connect guardrail services (content filters, anomaly detection, cost monitors) to the same control plane that handles Pause/Stop.
  * Distinguish in logs whether a human or a guardrail triggered a stop event.

* **Resilience and reliability**

  * Ensure that issuing a Pause/Stop command is idempotent and retriable.
  * Test kill switch behaviors regularly (for example, as part of chaos engineering or incident response drills).

## Example Scenarios

### Scenario 1: Code Refactoring Agent

* A developer starts an agent to refactor a legacy API module across dozens of services.
* The agent outlines a plan: analyze dependencies, propose refactors, open pull requests, and run tests.
* As refactoring begins, the control strip shows **Pause** and **Stop**.
* After observing early diffs, the developer hits **Pause**:

  * The agent finishes the current file’s changes and stops.
  * The UI shows “Paused at step 2 of 5 – 3 pull requests opened; no changes merged.”
  * The developer narrows scope to only two critical services and hits **Resume**.
* Later, a failing test appears; the developer hits **Stop**, reviews all created pull requests, and uses “Undo last batch” for one that looks unsafe.

### Scenario 2: CRM Cleanup Agent

* A revenue operations manager runs a “Data Hygiene Agent” to merge duplicate accounts.
* The agent runs in **preview mode**, generating a batch of proposed merges.
* The manager approves the plan and starts the run; Pause/Stop controls appear.
* After ten minutes, early results look good, but auto‑generated notes appear too aggressive.
  The manager:

  * Pauses the run.
  * Adjusts settings to use more cautious notes.
  * Resumes from the next step, leaving previous changes intact.
* Later, an anomaly detector flags a spike in merges for a particular region and automatically stops the run, surfacing an alert and a link to review that region’s changes.

### Scenario 3: Observability / DevOps Agent

* An observability agent detects an incident and starts a remediation run, including scaling services and toggling feature flags.
* On‑call engineers see the run in a “Live Remediations” dashboard, with a clear **Stop all agent actions** button.
* When a risky change is proposed (e.g., database schema adjustment), the agent pauses itself and requests human approval.
* After manual review, the team either resumes or stops the run and uses logs to annotate the incident timeline.

## Checklist

**Control visibility and semantics**

* [ ] Pause and Stop controls are always visible while a run is active.
* [ ] Labels and icons are consistent across all surfaces.
* [ ] Users can clearly distinguish Pause, Resume, and Stop, and understand scope.

**State handling**

* [ ] Runs have well‑defined states (Running, Paused, Stopped, Completed, etc.).
* [ ] Transitions (Pausing, Stopping) are represented and explained.
* [ ] State is resilient across reloads, reconnects, and client changes.

**User experience**

* [ ] Pausing shows what has been done and what remains.
* [ ] Stopping shows consequences and, where possible, rollback options.
* [ ] Automatic guardrail‑triggered stops are clearly explained in the UI.

**Governance and safety**

* [ ] Appropriate roles can pause/stop runs; sensitive controls are protected.
* [ ] Logs and audits capture who initiated each state change and why.
* [ ] Global or agent‑level kill switches exist for high‑risk contexts.

**Implementation**

* [ ] Workflows are decomposed into atomic, resumable steps with checkpoints.
* [ ] Backend supports reliable interruption of tool calls and workflows.
* [ ] Kill switch behaviors are tested regularly in staging or via drills.

This pattern, when properly implemented, transforms agentic AI from a black‑box automation risk into a controllable, inspectable collaborator that aligns with the expectations of modern B2B and B2C web applications.
