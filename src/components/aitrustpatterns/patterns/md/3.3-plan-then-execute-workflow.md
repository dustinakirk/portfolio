## 3.3 Plan-then-Execute Workflow (Unified Stream Variant)

A conversational workflow where multiple AI agents operate within a **single, unified chat stream**. Agents propose explicit, editable plans for multi-step or risky tasks, while a **navigation-based Action Shelf** ensures pending requests don’t get lost in the scroll history – even when several agents are talking at once.

*Last updated December 2025*

---

## Overview

The Plan-then-Execute Workflow pattern introduces an explicit planning phase into conversational AI workflows. Instead of immediately acting on a request, an agent surfaces a structured plan as part of the chat, invites refinement, and only then proceeds to execution.

In a **Unified Stream environment** – where DevOps, CRM, and Data agents all converse in the same thread – messages move quickly. A plan proposed by one agent can easily be pushed off-screen by subsequent messages from other agents.

This pattern solves the “lost context” problem by introducing a **Navigation Action Shelf**:

* The shelf **does not duplicate the controls** (buttons). Approval, edit, and reject actions remain attached to the **inline plan card** in the chat.
* Instead, the shelf acts as a persistent **“To-Do List” of shortcuts**. Clicking an item on the shelf instantly scrolls the chat history to the specific plan card requiring attention.

This ensures that:

* Action requests don’t get buried in fast-moving threads.
* The user can **continue messaging any agent** while actions are pending.
* Approval, pause, cancel, and other controls are always one click away **by jumping straight to the relevant inline plan card**.

---

## Problem

Without a plan-then-execute pattern, agentic systems tend to behave as opaque “black boxes”:

* **Hidden intent and side effects**
  The agent receives a natural language request and immediately performs tool calls or data mutations.

* **Over- or under-confidence in the agent**
  Users avoid powerful agent capabilities, or they over-trust them.

* **High cost of misunderstanding**
  Ambiguous instructions can lead to large-scale errors (e.g., mass updates, production deployments).

In **multi-agent, fast-paced conversations**, additional problems appear:

* **Action requests get buried**
  Approval prompts, plan cards, and confirmations from one agent scroll off-screen as other agents post updates, leaving the user unaware that actions are blocked on them.

* **Fragmented control surface**
  Each agent requests actions “inside” its own chat messages, so the user has to scroll up to find what’s pending and where to act.

* **Context-switching friction**
  Users want to keep talking to another agent (e.g., debugging with DevOps) while a plan from a different agent (e.g., CRM cleanup) awaits approval. If control is tied to a particular message in history, that flow becomes clumsy.

In a **single, unified conversation with multiple agents**, these issues concentrate into a specific set of failure modes:

* **Scroll Blindness**
  A user asks the DevOps agent to scale a database. While reading the plan, the CRM agent jumps in with a question about lead cleanup. The DevOps plan is pushed up and off-screen. Out of sight, out of mind.

* **Fragmented Context**
  Users often forget which agent is waiting on them. They might reply to the CRM agent, forgetting that the DevOps agent is effectively “paused” waiting for approval.

* **Redundant UI**
  Duplicating full approval controls (Approve/Reject buttons) into a global header can be dangerous if the user doesn’t see the full context of the plan (steps, risks) before clicking.

The Unified Stream Plan-then-Execute pattern addresses this by **keeping controls attached to the context (the message)**, while using the shelf strictly for **visibility and navigation**.

## Pattern Anatomy

### Core Item: The Inline Plan Card

The central object is the **Execution Plan Card** rendered directly in the chat stream by the specific agent.

* **Location**
  Inside a chat message for the agent that proposed it (e.g., from DevOps, CRM, or Data).

* **Content**

  * Step-by-step breakdown of the intended actions.
  * Risk analysis and impact assessment.
  * Resource requirements or affected entities (tables, accounts, services).

* **Controls**

  * “Approve”, “Edit”, and “Reject” buttons live **on the card itself**, ensuring the user reads the plan before acting.
  * Optional affordances for simulation, dry-run, or environment selection (sandbox vs production).

* **Metadata (per agent / conversation)**
  Even though the user sees an inline card, the system still maintains plan identity:

  * `plan_id`
  * `agent_id` / `agent_name`
  * `conversation_id` or `space_id`
  * `environment` (e.g., `sandbox`, `staging`, `production`)
  * `risk_level` (e.g., `low`, `medium`, `high`)

Multiple plans can exist concurrently across agents – e.g., a **“CRM Cleanup Plan”** from the CRM agent and an **“Email Campaign Optimization Plan”** from the Marketing agent – but they all appear inline in the **same unified stream**.

### Core Object: The Navigation Action Shelf

A compact **Navigation Action Shelf** sits immediately above the chat message input bar, visible regardless of which agent the user is currently addressing.

> In earlier versions, a “Global Action Shelf” also contained direct action controls. In the Unified Stream variant, the shelf is **navigation-only**: it surfaces what needs attention and jumps you to the right place in history.

#### Purpose

* **Visibility**
  Shows a count of how many plans are currently blocked or awaiting input (e.g., “2 Actions Pending”).

* **Navigation**
  Acts as a bookmark bar. Clicking an item scrolls the unified feed to that specific message (the plan card or confirmation point).

* **Non-blocking presence**
  Keeps the user aware of pending actions without freezing the conversation or forcing a response.

#### Elements

* **Shelf header / summary**

  * Text like: “2 Actions Pending” or “3 actions awaiting your input”.
  * Optional filter dropdown: `All · Approvals · Reviews · Blocks`.

* **Navigation chips / cards** (one per pending action or plan)

  * Agent avatar + name (e.g., “DevOps Assistant”, “CRM Assistant”).
  * Short label (“Prod DB Scaling”, “Approve CRM Cleanup Plan”).
  * Status text (`Needs approval`, `Needs info`, `Paused`, `Running (blocked)`).
  * Optional risk/environment indicator:

    * Icon + label such as `Live data`, `Sandbox`, `High impact`.
  * **Primary affordance**:

    * A “Jump” or “Link” icon (↗) and/or “Open” label indicating **navigation**, not immediate execution.

* **Expand / collapse**

  * The shelf can collapse into a single line (“2 actions pending ▾”) to avoid clutter but remains visible when there is work to do.

#### Behavior

* **Click interaction**

  * Clicking a chip **smooth-scrolls** the chat view to center the target message.
  * The target message briefly **highlights or flashes** (e.g., a 1–2 second background fade) to orient the user in dense history.

* **Lifecycle**

  * The shelf **appears** when a plan enters a “pending user input” state:

    * `Awaiting approval`
    * `Needs info`
    * `User confirmation required`
  * It **updates live** as plans move between states (`pending → running → done`).
  * It **disappears automatically** once the last pending item is resolved (e.g., the user clicks “Approve” or “Reject” on the inline card).

The shelf is **non-modal**: it does not block typing or switching agents. It simply follows the user as a persistent reminder and navigation layer.

---

## Behavior & Lifecycle

### 1. Proposal & Shelf Appearance

1. The user issues a complex or high-impact prompt in the unified stream.
2. Agent A (e.g., DevOps) analyzes the request and posts an **inline Plan Card** in the chat:

   * The card includes steps, risks, and controls (Approve/Edit/Reject).
   * Execution is **paused** (no writes) for that plan until an approved state exists.
3. As the message renders in a `waiting_approval` state:

   * The plan **registers itself** with the Shelf Manager.
   * The Navigation Action Shelf slides up, adding a shortcut chip for this plan (e.g., “Prod DB Scaling – Needs approval”).

Key nuance: the shelf is **not a modal**. The user can ignore it for now and keep typing, including to other agents.

### 2. Context Switching (The “Lost” Plan)

1. Agent B (e.g., CRM) posts a follow-up question or suggestion.
   The DevOps plan card gets pushed off-screen.
2. The Action Shelf remains visible, showing “1 Action Pending” for Agent A.
3. The user can continue interacting with Agent B (or others) while Agent A’s plan is effectively “blocked on approval”.

This visual layer prevents the system from silently stalling because a key plan scrolled out of view.

### 3. Navigation & Review

When the user is ready to address the blocked work:

1. They click the DevOps chip on the shelf.
2. The interface **scrolls up** to reveal the original Plan Card.
3. The card briefly **highlights** to show “this is what you jumped to”.
4. The user reviews the plan details **in context**:

   * Prior messages that led to the plan are still visible above.
   * Any subsequent clarifications requested by the agent remain nearby in the thread.

If the plan requires clarifications (e.g., missing parameters), the user can answer in-line. The plan may update its content and state accordingly, and the chip label/state on the shelf updates to match (e.g., `Needs info → Needs approval`).

### 4. Execution & Cleanup

1. The user clicks **“Approve”** on the inline Plan Card itself (not on the shelf).
2. The plan transitions from `waiting_approval` to `running`:

   * The agent begins executing the plan step by step.
   * The agent posts progress updates in the same unified stream.
3. The Shelf Manager detects the state change:

   * If the plan no longer requires user input, its chip is **removed** from the shelf.
   * If no actions remain pending, the shelf hides completely.

During execution:

* The corresponding chip may **reappear** if execution blocks on user input mid-way (e.g., `Needs confirmation to proceed with step 3`).
* The chip’s status text reflects the latest state, such as:

  * “Running – blocked on confirmation”
  * “Running – validation failed (needs input)”

## Interaction & States

This pattern introduces an additional explicit state to model cross-agent pending work.

### Additional State: **Multi-Agent Pending Actions**

* **Definition**
  At least one agent has a plan or step in a state that requires user input to proceed:

  * `Awaiting approval`
  * `Needs info`
  * `User confirmation required`

* **UI behavior**

  * The Navigation Action Shelf is visible with:

    * A summary of total pending items.
    * Individual chips for each agent/plan.
  * Each chip shows:

    * Agent identity (avatar + name).
    * Plan or action title.
    * Current state (e.g., `Needs approval`).

* **User expectations**

  * The user can temporarily **ignore** the shelf to continue chatting.
  * Returning to clear the shelf is easy and always **one click away** via a chip.
  * Clearing all pending items (approve/reject/answer) hides the shelf again.

## Variants

### Multi-Agent Action Center Variant

For environments with many agents and complex workflows, the Plan-then-Execute pattern may be paired with a richer **Action Center**:

* A dedicated panel or page listing:

  * All active plans across agents.
  * Their states, environments, and risk levels.
  * Who (which human) is responsible for approvals, if multiple people share a workspace.

* **Deep-linking**

  * From a Navigation Shelf chip → directly into the Action Center view for that specific plan.
  * From the Action Center back into the unified stream at the corresponding message.

* **Filtering**

  * By agent, risk level, environment (sandbox/live), or “assigned to me”.

In this variant, the **Navigation Action Shelf above the input bar** acts as a lightweight, in-context teaser of the Action Center: **quick navigation + a link** to the full triage view when the user needs to manage many pending actions.

## Implementation Notes

### Plan Representation (multi-agent fields)

Extend the plan object to include:

* `plan_id`
* `agent_id` / `agent_name`
* `conversation_id` or `space_id`
* `environment` (e.g., `sandbox`, `staging`, `production`)
* `risk_level` (`low`, `medium`, `high`)
* `requires_user_action` (boolean)
* `user_action_type` (`approval`, `clarification`, `confirmation`, etc.)
* `visible_in_action_shelf` (boolean)
* `short_label` (for compact chip display, e.g., “Prod DB Scaling”)

### Action Shelf Orchestration

* The **orchestrator layer** (above individual agents):

  * Listens for **state transitions** on plans:

    * `Draft → Awaiting approval`
    * `Running → Needs info`
    * `Paused → Awaiting resume`
  * Synchronizes these into a **single list of “action items”** rendered in the Navigation Action Shelf.

* Registration / deregistration:

  * When an inline plan component renders with `status="waiting_approval"` (or any `requires_user_action` state), it **registers** itself with the Shelf Manager.
  * When the state changes to `running` or `done`, it **deregisters** so the chip can be removed.

* Shelf items should expose callbacks that **navigate to context**, not perform actions:

  * `onNavigateToPlan()`
  * `onHighlightTarget()`

* Keep the shelf **stateless in the front end**, driven entirely by server-side / orchestrator state, to avoid drift between the chips and the messages they reference.

### State Synchronization (Unified Stream)

* The shelf and the chat stream must stay in **perfect sync**:

  * The source of truth is the plan/message state (e.g., `waiting_approval`, `running`, `done`, `error`).
  * Chips should be regenerated or reconciled whenever message state changes, not hand-edited on the client.

* Recommended implementation:

  * Each plan card exposes a unique `message_anchor_id`.
  * The Shelf Manager holds `{ plan_id, message_anchor_id, state, label, agent }`.
  * The chat UI knows how to scroll to `message_anchor_id` on click.

### Visual Orientation

When the shelf triggers a scroll:

* Apply a temporary **visual cue** (e.g., a 2-second yellow background fade) on the target message.
* Consider a micro “ping” animation on the plan card header to reinforce “this is where you landed”.
* Avoid excessive motion for accessibility (provide a reduced motion mode).

### Mobile Considerations

On mobile and small screens:

* The shelf should take up **minimal vertical space**.
* Consider a collapsed view like `“2 Actions ^”` that expands into a full list of chips when tapped.
* Ensure that:

  * The chat input remains easily accessible.
  * Shelf expansion doesn’t obscure the context of the message the user is currently typing.

### Non-Blocking User Experience

* Avoid modals that lock the entire workspace for a single agent’s plan.
* Favor:

  * Inline cards in the agent’s thread.
  * The Navigation Action Shelf for **quick navigation** back to where decisions are needed.
  * Optional side panels (on larger screens) for “full plan detail” so the main message stream doesn’t get overwhelmed.

### Accessibility & Notification

* Use:

  * Badges and icons on the Navigation Action Shelf (e.g., numeric indicators for pending actions).
  * Optional subtle sounds or toasts when:

    * A new plan requires approval.
    * Execution is blocked waiting on the user.
    * A long-running plan completes.

* Always pair iconography with text labels (e.g., “Live data”, “High impact”) to avoid color-only signaling.

* Ensure keyboard navigation can:

  * Focus each chip on the shelf.
  * Activate the navigation action (jump to plan).
  * Move between chips and back to the input field efficiently.
