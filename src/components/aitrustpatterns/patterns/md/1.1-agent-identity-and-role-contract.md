# 1.1 Agent Identity & Role Contract

An explicit, always-available “role contract” that tells users who the AI agent is, what it can and can’t do, and what it has access to—so expectations, safety, and trust stay aligned.

*Last updated December 2025*

---

## Overview

Agentic AI in products does not just answer questions—it acts: editing records, sending messages, orchestrating workflows, and making recommendations that impact money, customers, or employees. Users rapidly form mental models and even “relationships” with these agents, especially in conversational or avatar-based experiences. Misunderstandings about what an agent is and what it can do are a central source of frustration and mistrust.

The **Agent Identity & Role Contract** pattern makes that relationship explicit. It bundles:

* Who the agent is (identity, domain, role)
* What it is responsible for (capabilities)
* What it will *never* do (limits and guardrails)
* What it is connected to (data sources, tools, environments)
* How oversight works (draft vs. live actions, approvals, logging)

This information is exposed as a consistent UI surface: an agent header or card that is always present where the agent appears, plus a deeper “Role & access” or “What I can do” panel.

The pattern is particularly important in B2B/B2C web applications where agents touch production data (CRMs, finance tools, HR platforms, security systems) and where governance and accountability requirements are strict or evolving.

---

## Problem

Without an explicit role contract, AI agents introduce invisible risk and visible confusion:

* **Misaligned expectations and trust breakdowns**
  Users import assumptions from marketing, prior tools, or anthropomorphic design cues (“It has access to everything”; “It’s basically a human rep”). When those expectations are violated—e.g., the agent cannot take an action they assumed it could, or takes an action they never expected—trust erodes quickly.

* **Unclear data and tool access**
  Many agentic systems connect to core business platforms (CRM, billing, messaging, analytics). If users cannot see which systems are connected and with what scopes, they may overshare sensitive information or accidentally approve high-risk actions.

* **Ambiguous accountability and unsafe reliance**
  When it is not obvious whether the agent is “just suggesting” or actually executing changes, people either over-trust (blindly approving actions or assuming something is handled) or under-trust (ignoring useful automation). Clear communication of the system’s role, capabilities, and limits is necessary to calibrate reliance.

A clear Agent Identity & Role Contract addresses these issues by making the relationship between user, agent, and system explicit and testable.

## When to Use This Pattern

* **The agent can act on the user’s behalf**
  For example:

  * Updating CRM records or product data
  * Creating or modifying tasks, tickets, or issues
  * Drafting and optionally sending emails or messages
  * Triggering automations or workflows in other systems

* **The agent touches production or regulated data**
  For example, access to:

  * Customer or patient PII
  * Financial transactions and invoices
  * HR records and performance data
  * Security configurations and access rights

* **The agent appears in multiple product surfaces**
  The same agent shows up:

  * In a global sidebar
  * Inline in tables and detail pages
  * Inside confirmation modals
  * In automation builders or admin consoles

* **The agent’s role or powers can change over time**
  New tools are connected, scopes change, or “draft-only” capabilities graduate into “can execute changes” modes.

* **Governance and auditability matter**
  Security, compliance, or customer stakeholders need a clear, inspectable description of each agent’s powers and data usage.

## Probably Overkill When...

* **The AI is a narrow, obvious feature—not a “teammate” or “agent”**
  For example, ranking, smart filters, or “improve writing” controls that clearly operate only on the current object.

* **The feature is read-only and low-risk**
  For example, “summarize this article”, “explain this metric”, or “suggest tags” where no actions are taken in external systems.

* **The context itself strictly constrains behavior**
  A small inline affordance with copy like “We’ll only use this to rewrite your text here; nothing is stored or shared” may suffice.

* **Internal prototypes that never touch real users or real data**
  For lab experiments or concept tests, a lighter version (simple label + one sentence) is often enough.

## Pattern Anatomy

At a high level, this pattern is an always-available contract UI for the agent:

* A **compact agent header/card** that is visible in every interaction with that agent.
* A **Role & Access panel** that provides a structured, detailed breakdown of identity, capabilities, limits, and connections.

### Entry Points

* **Primary: Agent header / card in the main surface**

  * Pinned at the top of:

    * Chat interfaces
    * Side panels / drawers
    * Agent-powered task views or canvases
  * Contains:

    * Agent name
    * Avatar or icon (distinct from human avatars)
    * Short role tagline
    * A “Role & access” / “What I can do” link

* **Secondary: Inline agent chips or affordances**

  * Instances where the agent proposes actions:

    * “Ask Revenue Ops Agent to clean this account”
    * “Let AI plan this sprint”
  * Hover or click reveals a popover with core contract snippets and a link to the full panel.

* **Contextual: Permissions and confirmation surfaces**

  * Toasts, banners, or modals that include contract-derived statements:

    * “This agent can update lead fields but cannot delete records.”
    * “This agent will draft an email and ask you to send it.”

* **Administrative: Org / workspace AI settings**

  * Admin pages listing:

    * All agents in the workspace
    * A compact version of each role contract
    * Controls to adjust scopes or deactivate agents

### Core Item / Object

The key repeated unit is a **Role Contract Section**: a self-contained, testable statement about one aspect of the agent.

Each section typically includes:

* **Label**
  Examples:

  * “Who I am”
  * “What I can do”
  * “What I will not do”
  * “Connected tools”
  * “Data I can access”
  * “Approvals & oversight”

* **Description / statement**
  Plain-language, verifiable text, for example:

  * *Identity*

    * “I help clean CRM data and propose SDR cadences.”

  * *Capabilities*

    * “I can create, update, and merge contacts in Salesforce.”
    * “I can draft Outreach sequences and playbooks.”

  * *Limits*

    * “I cannot delete records.”
    * “I will not send emails without your approval.”

  * *Data & tools*

    * “I can see lead and contact fields; I cannot see opportunity notes or email content.”
    * “Connected to: Salesforce (read/write on leads & contacts), Outreach (draft-only), HubSpot (read-only analytics).”

* **Controls**
  Inline actions or toggles, such as:

  * Enable/disable specific capabilities (“Allow auto-merge duplicates”).
  * “Request more access” or “Disconnect integration”.
  * “View recent actions” / “View audit log”.

* **Optional metadata**

  * Risk level: “Draft-only”, “Requires approval”, “Can execute changes”.
  * Status: “Beta”, “Experimental”, “Generally available”.
  * Ownership: “Configured by Revenue Ops Admin – 3 days ago”.
  * Environment: “Sandbox only” vs. “Production”.

Together, these sections compose the Role & Access panel that can be opened from any surface where the agent is visible.

### Behavior & Lifecycle

1. **Initial introduction / first-run**

   * On first exposure, the user sees an introduction card or setup step:

     * Agent name and avatar.
     * One-line role description (“Revenue Ops Agent – manages CRM hygiene & SDR cadences.”).
     * Two short lists:

       * “Trusted for: ✅ Update leads, ✅ Deduplicate contacts, ✅ Draft cadences.”
       * “Will not do: 🚫 Delete records, 🚫 Send emails without approval, 🚫 Change pipeline stages.”
   * A primary action opens the full Role & Access panel; a secondary action lets users start interacting.

2. **Permission grant & configuration**

   * When connecting to external tools (Salesforce, Slack, ticketing, billing), a permission dialog:

     * Lists each system and the exact operations requested (read, write, send, delete, etc.).
     * Explicitly calls out high-risk scopes (e.g., delete, send, approve).
   * The role contract is generated from these scopes rather than manually written copy, aligning documentation with enforcement.

3. **Normal operation**

   * During everyday use:

     * The agent header remains visible and consistent.
     * Users can access the Role & Access panel at any time.
     * The agent’s messages refer back to the contract when relevant:

       * “I have drafted an email but cannot send it myself because I’m configured as draft-only.”

4. **Boundary handling (out-of-scope requests)**

   * When users ask for something outside the contract (e.g., “Delete all leads from this campaign”, “Approve this contract”), the agent:

     * States the limitation clearly:

       * “I’m not allowed to delete records or approve contracts.”
     * Offers a safe alternative:

       * “I can identify risky records and prepare a list for you to review.”

5. **Changes to capabilities or permissions**

   * When the agent gains or loses capabilities (e.g., new integration, new “auto-run” mode):

     * The system updates the role contract.
     * A banner or modal summarizes the diff:

       * “New: Ops Agent can now send emails after your review.”
     * High-risk changes may require explicit user or admin confirmation.

6. **Incident response and audit**

   * In case of surprising behavior or user complaints:

     * The Role & Access panel exposes recent actions, with links to a full audit log.
     * It is possible to verify whether the agent acted inside its stated contract or not.
   * This supports AI accountability practices where documented capabilities and observed behavior must match.

7. **Revocation and offboarding**

   * From the contract panel or workspace settings, users or admins can:

     * Revoke specific scopes (e.g., writing to Salesforce).
     * Disconnect tools entirely.
   * After revocation:

     * The contract and header update to reflect reduced capabilities (“I can no longer update CRM data because Salesforce access was revoked.”).
     * The agent gracefully explains limitations in subsequent interactions.

## Content & Microcopy Guidelines

* **Always disclose that it is AI**
  Use phrasing like “I’m an AI agent that helps with…” rather than implying a human operator.

* **Use “I can / I can’t / I will not” framing**

  * “I can: analyze, compare, and propose updates to your pipeline.”
  * “I can’t: approve contracts or modify billing settings.”
  * “I will not: send external messages or delete data without explicit approval.”

* **Make statements specific and testable**
  Avoid vague promises (“I’m always accurate”), and instead describe behavior in concrete terms:

  * “I cross-check leads across Salesforce and HubSpot to identify likely duplicates.”

* **Be careful and intentional with anthropomorphism**

  * Moderate anthropomorphic cues (name, avatar, conversational tone) can make agents feel more approachable and improve perceived trust and satisfaction.
  * At the same time, advanced agents can become manipulative if anthropomorphism is not balanced with clear limits and disclosures.
  * Avoid implying genuine emotion or consciousness (“I care deeply about your customers”); focus on function and constraints.

* **Highlight guardrails as a feature, not a disclaimer**
  Elevate safety language, for example:

  * “All external emails require your approval.”
  * “High-impact changes require admin review.”

* **Keep surface copy short, details deep**

  * At the header level, focus on:

    * Role tagline
    * 2–3 bullets for “Trusted for / Will not do”
  * Reserve detailed data and permission breakdowns for the panel.

## Interaction & Visual Details

* **Persistent agent header / card**

  * Located at the top of:

    * Chat or command interface
    * Side panel or “copilot” region
  * Contains:

    * Avatar/icon distinct from human avatars
    * Agent name and succinct role line
    * Quick summary of mode (e.g., “Draft-only”, “Can execute changes”)
    * Entry point to Role & Access panel

* **Progressive disclosure**

  * Surface UI:

    * Simple, scannable summary of identity and key limits.
  * Panel:

    * Tab or section layout for:

      * Overview
      * Capabilities
      * Limits & guardrails
      * Data & tools
      * Recent actions / logs
      * Settings

* **Risk communication**

  * Use consistent, non-alarming indicators:

    * Text tags (“Draft”, “Needs approval”, “Executes changes”).
    * Icons, labels, or color accents that differentiate modes without resorting to red-alert aesthetics.

* **Responsive behavior**

  * On smaller viewports:

    * Collapse header to a compact bar or “agent chip” near the input field:

      * “Ops Agent · Draft-only · Role & access”

* **Visual consistency**

  * The agent’s visual identity (name, icon) remains consistent:

    * Across chat, inline suggestions, notifications, and admin screens
    * Across different products in a suite, where applicable

## Implementation Notes

### Data & Permissions

* **Generate the contract from real permissions**
  Use structured permissions (scopes, RBAC, tool configs) as the single source of truth for:

  * “Trusted for / Will not do” bullets
  * Data access lists
  * Risk tags

* **Model capabilities as structured config, not hard-coded text**
  For each tool, track data such as:

  * System name
  * Resources (e.g., Lead, Contact)
  * Allowed operations (create, update, merge)
  * Denied operations (delete, approve)
  * Environment (sandbox, production)

  This configuration should drive:

  * Backend enforcement
  * Agent planning/tool selection
  * UI copy in the contract

* **Align with AI transparency and documentation practices**
  Treat the role contract as a user-friendly front-end to model and system documentation (“model cards”, “system cards”).

### Multi-tenant & Admin Considerations

* **Org-level defaults, team-level constraints**

  * Org admins define:

    * Default capabilities and limits for each agent.
  * Teams can:

    * Add tighter constraints per region or business line (e.g., stricter HR rules in some jurisdictions).

* **Versioning and change management**

  * Maintain:

    * A version number for each agent configuration.
    * A change log for what changed and why.
  * Trigger in-product notifications when a version introduces new powers or reduces guardrails.

* **Auditability**

  * Store:

    * Who granted which permissions and when.
    * For each action, which agent configuration version applied.
  * Provide exportable views for security/compliance.

## Edge Cases & Failure Modes

* **Contract drift vs. reality**

  * Risk: The contract says “cannot delete records”, but a new integration or bug enables deletion.
  * Mitigation:

    * Derive contract copy from permissions.
    * Run automated checks that compare current config with rendered contract before deployment.

* **Technical failure disguised as policy**

  * Risk: The agent says “I can’t access Salesforce” when the real issue is a temporary outage.
  * Mitigation:

    * Separate “not allowed” (policy) from “currently unable” (incident).
    * Keep the contract focused on policy; show transient errors separately.

* **Different users, different powers**

  * Risk: Contract appears global but access differs per user role or workspace.
  * Mitigation:

    * Make it clear when statements are per-user (“In your account, this agent can…”).
    * Provide admins with an org-wide view.

* **High-stakes domains**

  * Risk: Misinterpretation of agent outputs as professional advice (health, legal, financial).
  * Mitigation:

    * Use stronger, legally reviewed limits in the contract (“Not a medical device”, “Not a legal opinion”).
    * Ensure outputs are clearly framed as informational or draft-only.

---

## Anti-Patterns

Avoid these patterns that undermine trust and safety:

* **Mystery Agent**

  * No name, no role, no visible permissions; just an “Ask AI” button that sometimes edits data or sends messages.

* **Masquerading as a human**

  * The agent presents itself as a human representative until users discover otherwise. This kind of expectation violation is consistently linked to trust damage and negative sentiment.

* **Hand-wavy, generic disclaimers**

  * Tiny footnotes like “AI may be inaccurate” instead of clear, actionable limits (“I can’t change billing details.”).

* **Cute persona for serious power**

  * Highly anthropomorphic mascots and emotional language in systems that can move money, change privileges, or affect employment. Anthropomorphic cues increase trust and compliance, which can be dangerous without robust guardrails and clarity.

## Examples (B2B / B2C Web Application Scenarios)

### 1. Revenue Ops Agent in a Sales Platform (B2B)

* **Header**

  * Name: “Revenue Ops Agent”
  * Role line: “Manages CRM hygiene & SDR cadences.”

* **Trusted for**

  * ✅ Creating and updating leads and contacts in Salesforce
  * ✅ Identifying and merging duplicates (with review)
  * ✅ Drafting outreach sequences and tasks

* **Will not do**

  * 🚫 Delete any records
  * 🚫 Send emails or sequences without user approval
  * 🚫 Change opportunity stages or quotas

* **Data & tools**

  * Salesforce – read/write leads & contacts
  * Outreach – draft-only (no send)
  * HubSpot – read-only campaign analytics

### 2. Security Posture Agent in a SaaS Security Platform (B2B)

* **Header**

  * Name: “Security Posture Agent”
  * Role line: “Monitors SaaS risk and drafts remediation.”

* **Trusted for**

  * ✅ Scanning connected SaaS apps for risky configurations
  * ✅ Drafting remediation tickets and notifications
  * ✅ Prioritizing issues based on severity

* **Will not do**

  * 🚫 Change security settings automatically
  * 🚫 Grant or revoke access rights
  * 🚫 Approve exceptions or policy changes

* **Data & tools**

  * Read-only configuration access for connected apps
  * Ticketing system access to create draft issues

### 3. Campaign Co-Pilot in a Marketing Platform (SMB / B2C)

* **Header**

  * Name: “Campaign Co-Pilot”
  * Role line: “Helps plan and write campaigns.”

* **Trusted for**

  * ✅ Drafting email and SMS copy
  * ✅ Suggesting send times and audience segments
  * ✅ Summarizing campaign performance

* **Will not do**

  * 🚫 Launch campaigns
  * 🚫 Change billing or pricing settings
  * 🚫 Upload new contact lists

* **Data & tools**

  * Read limited audience metadata (segments, engagement scores)
  * Read-only access to past campaign results

## Telemetry & Evaluation

Instrument the pattern to understand whether it actually improves clarity and trust:

* **Contract engagement**

  * Percentage of users who open the Role & Access panel at least once.
  * Frequency of views around key events (first use, new permission grant, incidents).

* **Boundary metrics**

  * Count and categories of out-of-scope requests (“I’m not allowed to do that”).
  * Common misunderstandings to feed back into copy or training data.

* **Incident correlation**

  * Whether user complaints or risky behavior correlate with unclear or outdated contract copy.

* **Perceived clarity and trust**

  * Lightweight in-product pulse questions, such as:

    * “How clear is it what this agent can and cannot do?”
    * “Has this agent done anything that surprised you?”

Findings from mental-model and usability research consistently show that targeted explanations of capabilities and limits, provided in context, reduce expectation gaps and support more appropriate reliance on AI systems.

## Questions for Design & Review

Use the following checklist when reviewing an agent implementation:

* **Identity & role**

  * Can a first-time user answer, from the header alone:

    * Who this agent is?
    * What domain it operates in?
    * Whether it is AI vs. human?

* **Capabilities & limits**

  * Are “Trusted for / Will not do” statements:

    * Specific, concrete, and testable?
    * Consistent with the actual permissions and backend constraints?

* **Data & tools**

  * Is it clear:

    * Which systems the agent connects to?
    * What types of data it can read and modify?
    * Whether it operates in sandbox vs. production?

* **Oversight**

  * Is it obvious:

    * When the agent is drafting vs. executing?
    * What requires user approval or admin review?

* **Lifecycle & change**

  * When the agent’s powers change, is that:

    * Reflected in the contract?
    * Communicated in-product with a clear diff?

* **Governance**

  * Can admins:

    * View all agents and their contracts in one place?
    * Adjust scopes and modes (draft-only vs. execute)?
    * Access logs and version history for audits?
