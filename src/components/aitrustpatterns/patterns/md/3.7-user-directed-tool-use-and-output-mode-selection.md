# 3.7 User-Directed Tool Use & Output Mode Selection

Expose clear controls that let users determine *how* an AI agent responds (e.g., text, image, code, SQL, diagram) and *which tools* it may use, reducing ambiguity, surprises, and risky side effects.

*Last updated December 2025*

---

## Overview

User-Directed Tool Use & Output Mode Selection is a pattern in which the chat composer or surrounding UI lets users declare the desired *mode* and *tool scope* for the next AI action. Instead of leaving tool invocation entirely to the model, the interface surfaces explicit controls such as chips, segmented controls, dropdowns, or toggles like:

* **Output mode**: Text only, Code snippet, SQL query, Diagram, Image, Slide deck outline, etc.
* **Tool usage policy**: Auto, Ask before using tools, Tools off, or specific tool subsets.

This pattern typically appears in B2B/B2C web applications where an AI agent can:

* Call multiple tools (e.g., web search, internal knowledge base, CRM API, SQL warehouse, image generator).
* Produce content in different formats (e.g., prose explanation, charts, code, structured JSON or YAML).

By making mode and tool choice explicit, the pattern strengthens mental models, supports safety and compliance, and reduces the perception of the AI as a hidden “black box.” It also provides a clean bridge to related patterns such as **Scoped Permissions & Tool Consent (3.5)** and **Tool Usage Indicators (5.3)**.

**Example – Embedded semi-interactive pattern**

In a product analytics platform, the chat composer shows a compact control row above the input:

* Mode chips: **Chat**, **SQL only**, **Explain + SQL**, **Chart**, **Dashboard draft**.
* A tool usage toggle: **Tools: Auto · Ask · Off**.

A data analyst drags a CSV into the chat. The system infers that a structured output is likely and pre-selects **Explain + SQL**. The analyst switches to **SQL only** and sets tools to **Ask**, because queries will run on a production database. The agent then:

* Proposes a SQL query with clear labeling:
  `Mode: SQL only · Tools: Database (pending confirmation)`
* Shows a “Run query” button and a short risk note before executing.
* After execution, updates the label to:
  `Used: Database (read-only) · Rows returned: 2,543`.

The UI keeps the mode chips visible for the next message, with an option to “Reset to default mode.”

## Problem

Without user-directed tool and mode controls, agentic systems commonly create friction and erode trust:

* **Opaque tool usage and side effects**
  Agents silently call tools such as web search, CRM APIs, or code execution environments. Users cannot easily tell *what* was used, whether data left the organization, or why an answer looks the way it does.

* **Output-type mismatch with expectations**
  Users may be expecting a concrete artifact (SQL, code, diagram, slide outline) but receive narrative prose or a mix of formats. This forces extra back-and-forth and manual translation.

* **Safety, compliance, and risk concerns**
  In regulated or high-stakes domains, some tools (e.g., write-access APIs, production databases, external web search) are acceptable only in specific contexts or with explicit consent. Silent tool usage increases anxiety and organizational resistance.

* **Difficult debugging and governance**
  When behavior varies between “runs” due to hidden tool calling, it becomes harder to audit what happened, reproduce issues, or tune the underlying orchestration.

* **Over-reliance or over-automation**
  Fully autonomous tool usage can encourage users to “lean back,” while some tasks actually require human judgment, review, or a step-by-step approach.

This pattern addresses these problems by making tool choice and output mode explicit, predictable, and explainable at the UI layer.

---

## When to Use This Pattern

* **Multi-tool agents with material side effects**
  Any agent that can read/write business data (CRM, ERP, marketing automation, observability platforms, HRIS, billing, etc.) or trigger external actions (emailing customers, scheduling tasks, updating records).

* **Multi-modal or multi-format responses**
  Systems that can generate text, code, diagrams, dashboards, slides, or images, where user intent around “what kind of result is wanted” is often underspecified in the natural language prompt.

* **Risk-managed or regulated workflows**
  Domains such as finance, healthcare, security, legal review, or compliance, where it matters *which* data sources and tools are used and whether external services are called.

* **Power-user or expert-oriented tools**
  Environments like IDEs, BI tools, cloud consoles, data science notebooks, or admin consoles, where users expect levers for precision control rather than fully implicit automation.

* **Enterprise deployments with differentiated permissions**
  Workspaces where tools are scoped by team, role, or environment (e.g., sandbox vs. production) and must not be called without clear affordances.

## Probably Overkill When...

* **Single-purpose assistants with one obvious modality**
  For example, a simple “rewrite this paragraph” assistant embedded in a text editor that only ever returns text and never calls external tools.

* **Low-stakes, purely informational chatbots**
  Marketing sites or FAQ bots that only answer from a static content set, with no external calls or side effects.

* **Strongly constrained flows with explicit wizards**
  When an existing wizard or form fully constrains the interaction (e.g., “Generate password suggestions”), and the only reasonable output is already fixed and low-risk.

* **Highly novice-focused experiences**
  On-boarding flows where exposing a dense mode matrix might overwhelm users; in such cases, simple presets or scenario templates may be sufficient.

## Pattern Anatomy

At a high level, this pattern adds an explicit “mode and tools strip” around the chat composer that:

* Communicates how the next AI action will behave.
* Scopes which tools are allowed to be called.
* Surfaces relevant safety and permission boundaries.

### Entry Points

* **Primary entry – Chat composer strip**

  * A mode selector (chips, segmented control, or dropdown) attached directly to the message input field.
  * Examples: “Chat”, “Image”, “Code”, “Diagram”, “SQL only”, “Explain + run”.

* **Secondary entry – Global mode selector for the agent**

  * A dropdown in the header of the agent panel: “Ask”, “Edit”, “Agent”, “SEO Expert”, “Debugging mode”.
  * Sets defaults that apply until changed, while still allowing per-message overrides near the composer.

* **Contextual entry – Inline controls in outputs or attachments**

  * “Re-run as…” contextual actions on prior messages (e.g., “Re-run as SQL only”, “Re-run using Web + Org Files”).
  * Mode presets attached to file uploads (“Summarize PDF”, “Extract table”, “Generate diagram from this”).

### Core Item / Object

The core unit is the **Mode & Tool Selector**, which typically includes:

* **Label**

  * Clear, outcome-oriented names like “SQL only”, “Image (draft sketch)”, “Chat + chart”, “No external tools”.
  * Optional icons for modality (text bubble, code brackets, chart, image, database, globe for web).

* **Description / statement** (tooltip or sub-label)

  * Short clarifications such as:

    * “Returns valid SQL for the connected warehouse.”
    * “May call external web search.”
    * “Read-only access to observability data.”
    * “No tools: model-only answer.”

* **Controls**

  * Single-select chips or segmented controls for mutually exclusive modes (e.g., Chat vs SQL only).
  * Optional multi-select or stacked combinations for richer flows (e.g., “Explain + chart”, “Chat + run SQL”).
  * Tool usage toggle, typically as:

    * **Auto** – Agent may call tools as needed.
    * **Ask** – Agent proposes tool use and waits for confirmation.
    * **Off** – Tools disabled for this message (or conversation).

* **Optional metadata**

  * Scope indicators: “Scope: This workspace”, “Environment: Sandbox”, “Sources: Web + Org files”.
  * Risk badges: “External data”, “Write access”, “Experimental”.
  * Status: “Requires approval”, “Disabled by admin”, “Coming soon”.

## Behavior & Lifecycle

This pattern spans several states across the conversation lifecycle.

1. **Initial state / defaults**

   * Each agent defines a sensible default mode, such as **Chat** with **Tools: Auto**.
   * Defaults are tailored to the agent’s primary purpose (e.g., a “SQL Assistant” might default to **Explain + SQL**; a “Design Assistant” might default to **Wireframe** or **Spec**).

2. **Context-aware pre-selection**

   * The system infers a likely mode based on context but does not hide the control:

     * Large table or CSV pasted → pre-select “Table / Chart” or “Explain + SQL”.
     * Screenshot uploaded → pre-select “Describe image” or “Redline UI”.
     * System-detected high-risk environment (e.g., production DB) → pre-select “Ask before tools”.
   * The mode and tool toggle remain visible and can be overridden at any time.

3. **User-directed selection before sending**

   * The user selects an output mode and tool policy before submitting the message:

     * Mode chips update their visual state (e.g., highlighted, underlined).
     * A compact summary appears near the send button:

       * “Mode: SQL only · Tools: Ask”
       * “Mode: Wireframe · Tools: Auto (Canvas + Image)”.

4. **Orchestration and tool resolution**

   * The orchestration layer receives the selected mode and tool policy as **strong hints or constraints**, for example:

     * Enable only specific tools (e.g., database-read, charting) and disable others (e.g., email, web search).
     * Configure tool-choice parameters (e.g., “tools off”, “tools available but must be requested”, “tool X required for this run”).
     * Adjust response format expectations (e.g., enforce JSON schema for “API payload” mode).

5. **Response with visible tool usage**

   * The agent message includes a compact label (aligned with **Tool Usage Indicators (5.3)**), such as:

     * “Mode: SQL only · Used: Warehouse (read-only)”
     * “Mode: Image · Used: Image generator”
     * “Mode: Chat · Tools: None (model-only answer)”.
   * Advanced users can expand this to see:

     * Which tools were available vs. actually used.
     * Whether the agent requested permission and what the result was.
     * Links to logs or execution details, where appropriate.

6. **Confirmation and execution for side-effectful tools**

   * For modes that imply write actions or external calls, the pattern often introduces a two-step flow:

     * First, the agent proposes an action: SQL to run, API call body, email draft, or infrastructure change.
     * Then, the UI surfaces a clear “Run”, “Apply”, or “Send” button, along with:

       * Scope summary (“Environment: Staging only”, “Affects 32 records”).
       * Optional diff or preview.
       * A reminder of the selected mode and tool usage policy.

7. **Persistence and preference management**

   * The system may persist the selected mode:

     * **Per-conversation**: Preserve mode across turns for a specific thread.
     * **Per-agent preference**: Let power users opt into a default mode (e.g., “Always start in SQL only”).

   * Provide a visible control for resetting:

     * “Reset to agent default mode”
     * “Stop remembering this mode.”

8. **Errors, fallbacks, and degraded behavior**

   * If a tool is unavailable, misconfigured, or blocked by policy:

     * The agent explains the limitation in-band.
     * The UI suggests alternative modes (“Tool offline; switch to ‘Chat only’?”).
     * The system avoids silently ignoring the chosen mode.

   * If the user-selected mode is incompatible with the request (e.g., “Image” mode but the request is strictly numerical grading):

     * The agent clarifies and suggests a better mode, while still trying to honor the original request.
     * The UI can pre-select a more appropriate mode on the next turn, but always keeps it visible and editable.

9. **Permissions and safety integration**

   * Modes that require extended access (e.g., production databases, external web search, third-party APIs) are visually distinct and integrated with **Scoped Permissions & Tool Consent (3.5)**:

     * Greyed-out chips with a padlock icon that open a lightweight permission sheet.
     * Short, contextual explanations of what data will be accessed and how.
     * Clear indicators when an admin has disabled certain modes or tools.

## States & Variants

Common variants of this pattern include:

* **Output format–only selector**

  * Only controls the output shape (text, code, diagram, “spec”), while tools remain mostly automatic but transparent.

* **Source / retrieval selector**

  * Modes to choose data sources such as:

    * “Web”, “Org files”, “Web + Org files”, “None”.
  * Particularly useful in enterprise knowledge search and research workflows.

* **Autonomy selector**

  * A tri-state tool usage policy:

    * **Auto** – Agent calls tools freely within allowed scope.
    * **Ask** – Agent proposes calls and waits for confirmation.
    * **Off** – Tools disabled; model uses its internal knowledge only.

* **Role or persona modes**

  * Modes that bundle tools, instructions, and tone:

    * “Ask” vs. “Edit” vs. “Agent” in developer or data science tools.
    * “SEO Agent”, “Support Agent”, “Ops Agent” in marketing or operations platforms.

* **Light vs. advanced mode pickers**

  * A minimal, opinionated set of modes for general users.
  * An expanded “mode drawer” for experts, offering fine-grained control over tools, sources, and response format.

## Interaction & Content Guidelines

### Naming and labeling

* Prefer **task- or outcome-oriented names** over technical jargon:

  * “Draft SQL query” vs. “SQL mode”.
  * “Explain and visualize” vs. “LLM + chart tool”.

* Make **risk and scope explicit** in labels or subtext:

  * “May use external web search.”
  * “Writes into CRM pipeline.”
  * “Read-only access to production metrics.”

* Avoid ambiguous or purely marketing terms such as “Smart”, “Pro”, or “Magic” without further explanation.

### Microcopy and messaging

* Use concise microcopy to indicate:

  * Which tools or data domains are in scope.
  * Expected latency (e.g., “May take up to a minute for deep analysis”).
  * When the AI will ask for confirmation before acting.

* In failure or mismatch states, favor explanatory messages:

  * “Chart mode requires tabular data. Paste a table or switch back to Chat.”

### Interaction patterns

* Ensure **mode selection is fast, reversible, and keyboard accessible**:

  * Tab through chips and toggles.
  * Use arrow keys to move between modes.
  * Provide visible focus states and ARIA roles for assistive technologies.

* Support **per-message overrides** even when a global agent mode is set.

* Consider **hover previews** or mini-descriptions when many modes exist.

## Implementation Notes (Orchestration Layer)

While the UI describes the pattern visually, two implementation aspects are critical for trust:

1. **Mapping modes to tools and configuration**

   * Each mode should map to:

     * A list of allowed tools (e.g., image generator, SQL executor, web search, org search, code interpreter).
     * Tool-choice policies (e.g., tools disabled, tools optional, specific tool required).
     * Response format constraints (e.g., must return JSON conforming to a schema, must return SQL only).

   * This mapping should be explicit and testable, avoiding “mode names that do nothing” in the backend.

2. **Alignment between selected mode and actual behavior**

   * Telemetry should capture:

     * Selected mode and tool policy at send time.
     * Tools actually invoked and their outcomes.
     * Whether the response format matched the mode’s contract.

   * Any misalignment (e.g., tools used when “Tools: Off” was selected) is a high-priority defect from a trust standpoint.

3. **Safety and policy enforcement**

   * Organization-level policies should gate which modes appear at all, rather than only failing at execution time.
   * Sensitive modes should obey environment flags (e.g., “No production writes via AI”).
   * System prompts or tool definitions should be consistent with UI messaging so that the model or agents do not attempt disallowed behavior.

## Edge Cases & Anti-Patterns

**Edge cases**

* **Missing or disabled tools**

  * When a user selects a mode that depends on an unavailable tool, the interface should:

    * Explain the issue.
    * Offer alternative modes that can fulfill a similar goal.
    * Optionally provide a link or instruction to enable the missing capability.

* **Cross-tenant or mixed-permission sessions**

  * In multi-tenant contexts, some modes may be available only for specific workspaces or roles.
  * The UI must dynamically reflect current permissions and avoid “ghost” modes.

* **Very long-running or multi-step actions**

  * Some modes (e.g., deep research, multi-stage workflow execution) may span multiple messages:

    * Provide clear progress states and allow users to pause or cancel.
    * Keep mode indication visible throughout long-running operations.

**Anti-patterns**

* **Ignoring the selected mode**

  * Allowing the agent to disregard an explicit mode choice (e.g., returning prose when “SQL only” is selected) quickly erodes trust.

* **Overloading the interface with modes**

  * Presenting a long, unstructured list of highly technical modes can overwhelm users. Grouping, presets, or progressive disclosure can mitigate this.

* **Hiding high-impact modes behind generic names**

  * Dangerous or high-impact tools (e.g., bulk edits, emails, infrastructure changes) should not be hidden under vague labels.

* **Silent escalation of capabilities**

  * Adding new tools or changing what a mode does without any UI indication can cause severe mismatches between user expectations and behavior.

## Example Scenarios

### Design system assistant (original use case)

In an enterprise design system portal, an embedded AI assistant supports designers and engineers. The composer row includes:

* Modes: **Chat**, **Figma-ready spec**, **Wireframe**, **Code snippet**.
* Tool usage toggle: **Tools: Auto · Ask · Off**.

A designer selects **Wireframe** and asks for “A homepage hero for a B2B SaaS”. The system:

* Uses internal layout and component libraries to generate a structured wireframe representation.
* Shows a label: “Mode: Wireframe · Used: Component library, Layout generator”.
* Provides secondary actions: “Copy to Figma plugin”, “Switch to Spec mode.”

### BI / analytics copilot

In a web-based BI suite:

* Modes: **Explain chart**, **SQL only**, **Explain + SQL**, **Build dashboard**.
* Sources: **Warehouse**, **Event stream**, **Logs** (multi-select).
* Tools: **Auto** or **Ask before running queries**.

When a data analyst selects **SQL only** with **Warehouse + Logs**, the orchestration:

* Enables read-only SQL tools scoped to those sources.
* Returns only SQL code, with no natural language explanation, because the consuming system expects a query artifact.
* Shows a clear label indicating tools and sources used.

### CRM copilot with compliance constraints

In a CRM platform:

* Modes: **Summarize contact**, **Draft email**, **Update pipeline**, **Research account**.
* Tool usage toggle and data source selector:

  * “Org data only”, “Org data + Web”, “Web only”.

The organization’s compliance policy disables “Org data + Web” for some roles, so that mode appears greyed-out with a tooltip explaining the policy. Selecting **Research account** uses only web and knowledge tools, with a visible label: “External web sources; customer PII not sent.”

## Accessibility Considerations

* Ensure all mode and tool controls are reachable and operable via keyboard only.
* Use ARIA roles (e.g., `role="tab"` for segmented controls, `role="button"` for chips) and proper labelling (`aria-label`, `aria-describedby`).
* Provide sufficient color contrast and icon alternatives so that state (selected, disabled, risky) is not conveyed by color alone.
* Announce mode changes and tool-usage state changes via live regions for screen readers when appropriate.

---

## Design & Implementation Checklist

* [ ] Does the agent expose all meaningful output modes and tool policies that affect behavior?
* [ ] Are mode names outcome-oriented, non-ambiguous, and understandable to target roles?
* [ ] Is the mode selector consistently visible near the composer, with minimal friction to change?
* [ ] Does the orchestration layer strictly honor “Tools: Off” and other explicit constraints?
* [ ] Are high-risk modes clearly labeled and integrated with permission / consent flows?
* [ ] Does each response clearly indicate which tools and sources were used?
* [ ] Are errors and unavailable tools handled with clear explanations and suggested alternatives?
* [ ] Are keyboard navigation, screen reader support, and contrast needs met for the selector UI?
* [ ] Are analytic events logged for selected mode, tool usage, and any mismatches for future tuning?
* [ ] Are changes to mode behavior or underlying tools communicated in-product to maintain trust?

## Related Patterns

* **3.5 Scoped Permissions & Tool Consent**
  Ensures that tool access is appropriately gated by role, workspace, and explicit consent; mode selection builds on this by exposing which tools are in play.

* **5.3 Tool Usage Indicators**
  Provides per-message transparency about what the agent actually did; essential for closing the loop between selection and execution.

* **Task Scoping & Goal Setting**
  Higher-level pattern for articulating goals, constraints, and success criteria before the agent acts; often paired with mode selection for clarity.

* **Preview & Confirmation for Side-Effectful Actions**
  Ensures that any write-action or external call is confirmable and auditable, frequently triggered from modes like “Run SQL” or “Apply change.”
