# 5.3 Tool Usage Indicators

Clear, contextual cues showing which tools an AI agent is using, what state each call is in, and how that activity interacts with data and systems.

*Last updated December 2025*

---

## Overview

Tool Usage Indicators make an AI agent’s interaction with external systems, data sources, and automations visible and understandable. Instead of a generic “thinking…” state, the interface distinguishes between:

* Pure model reasoning (no tools),
* Read-only tool use (search, retrieval, calculations),
* Write or side-effectful tool use (updating records, sending messages, triggering workflows).

This pattern typically appears directly in or near the chat surface of an AI assistant, in assistant sidebars, or within job/task detail views. It provides short, human-readable labels such as:

* “Searching internal knowledge base…”
* “Running SQL query on analytics warehouse…”
* “Preparing write to CRM (pending approval)…”
* “Creating Jira issue in Engineering project…”

The core idea is to align the user’s mental model with what the agent is actually doing behind the scenes: which systems are being accessed, whether operations are read-only or write, and what stage each operation is in (queued, running, awaiting approval, failed, completed). For higher-risk actions, indicators are paired with explicit review and approval controls.

Tool Usage Indicators integrate naturally with a Reasoning Glimpse or plan visualization pattern. Reasoning steps such as “Gather context” or “Update records” can be annotated with tool badges and live status, forming a coherent picture of both *why* the agent is doing something and *how* it is doing it.

## Problem

Without visible tool usage, AI agents feel like opaque black boxes with unpredictable side effects:

* **Unclear origin of answers**
  Users cannot tell whether a response came purely from the model, from up-to-date enterprise data, or from external web sources. This undermines trust and makes it difficult to judge reliability.

* **Hidden side effects and data changes**
  When agents can call APIs or modify systems-of-record, invisible writes become dangerous. Users may later discover that tickets were created, emails were sent, or records were updated without any clear indication of when or how.

* **Ambiguous “thinking” state**
  A single, generic typing or loading indicator conflates reasoning, tool calls, network delays, and approval waits. Users cannot tell whether the agent is actually working, waiting on a dependency, or stuck.

* **Weak auditability and incident analysis**
  In enterprise contexts, teams need to answer questions such as “Which tools did this agent use?”, “Which systems were modified?”, and “What data was accessed?” Without a structured record of tool usage, debugging and compliance reviews are slow and error-prone.

Tool Usage Indicators address these issues by revealing tool-driven activity in a structured, human-readable way, with clear distinctions between read-only and write operations and a visible lifecycle for each call.

---

## When to Use This Pattern

* **Agentic workflows with tool orchestration**
  Whenever an AI agent can call APIs, run code, execute workflows, or interact with third-party systems (CRM, HRIS, ERP, ticketing, analytics, cloud services).

* **Scenarios involving system-of-record changes**
  Any workflow where the agent can create, update, or delete records (e.g., sales opportunities, support tickets, HR records, financial entries) or send messages on behalf of a human.

* **Multi-source retrieval and RAG experiences**
  When the agent is expected to search across local documents, product logs, internal knowledge bases, and external web sources, and stakeholders care about which sources are being used.

* **Regulated or high-stakes domains**
  Compliance, finance, healthcare, HR, security, and legal workflows where data access and system changes must be transparent and auditable.

## Probably Overkill When...

* **Simple, local-only tasks**
  Short, single-turn completions such as rewriting text, translating content, or summarizing a short note where no external tools or data sources are involved.

* **Static, bounded operations with obvious behavior**
  Cases where a form or wizard already clearly controls which system is being used and exactly what will happen (e.g., a conventional “Create ticket” dialog) and the agent only assists with phrasing.

* **Low-impact, read-only queries**
  Informational queries against a single known source where the impact of tool usage is trivial and latency is low, and where standard loading indicators are sufficient.

## Pattern Anatomy

Tool Usage Indicators typically consist of:

* A compact, inline surface directly under or adjacent to the agent’s message in the chat UI, showing what tools are being used *right now*.
* An optional expanded view (side panel, drawer, or job detail page) that exposes a structured timeline of tool calls for deeper inspection and auditability.

### Entry Points

* **Primary entry point: inline tool status under agent messages**
  A short “Activity” or “Tools used” section appears beneath agent responses whenever tools are invoked. This is visible by default, but kept compact—often a single line per tool with icon, label, and status.

* **Secondary entry point: expandable activity details**
  A “View details”, “View tool activity”, or chevron button reveals an expanded list or timeline beneath the message. This view shows individual calls, durations, scopes, and error messages.

* **Contextual entry point: task / job detail view**
  For longer-running or asynchronous tasks, a dedicated detail page or modal surfaces the full tool usage timeline. This is typically accessed from notification toasts, job cards, or status banners, and is used for review, debugging, and audits.

### Core Item / Object

The core repeated unit is the **Tool Call Indicator**.

Each Tool Call Indicator represents a single tool invocation or a small batch of closely related calls. It answers three key questions at a glance:

1. *Which tool or system is involved?*
2. *What is the agent attempting to do with it?*
3. *What is the current status and impact?*

Typical structure:

* **Label**
  A concise, action-oriented description in domain language, for example:

  * “Searching product knowledge base…”
  * “Running SQL query on analytics warehouse…”
  * “Reading 24 HR records from People system…”
  * “Preparing 12 CRM updates (pending approval)…”
    The label communicates the tool’s purpose and the nature of the operation (read vs write), not internal implementation details.

* **Description / statement (optional)**
  One or two lines of additional context, such as:

  * “Filtering customer records from the past 90 days.”
  * “Drafting status updates for all at-risk opportunities.”
  * “Simulating changes in sandbox environment only.”

* **Controls**
  Inline actions depend on risk and context, and may include:

  * Cancel / stop call.
  * Retry failed call.
  * Open source system (e.g., “Open in CRM”).
  * Review pending changes or diffs.
  * Approve / reject a write operation.
  * Expand to view technical details (for advanced or debug modes).

* **Optional metadata**

  * Tool identity: icon, name (“CRM”, “HR system”, “Data warehouse”).
  * Access mode: read-only, write, or simulate.
  * Environment: Production, Sandbox, Test.
  * Scope: counts (“17 records”), entities (“3 tickets”), time ranges.
  * Status: Queued, In progress, Awaiting approval, Completed, Skipped, Failed.
  * Latency or duration (where meaningful).
  * Permissions: flags such as “Requires admin approval” or “Limited to this team’s data”.

* **Visual state & motion cues**

  * Status icon (spinner, checkmark, warning, pause).
  * Subtle animated progress indicators while the call is active.
  * Clear, static states when completed or failed.

### Behavior & Lifecycle

1. **Request and planning**

   * The user submits a prompt or action request.
   * The agent determines that one or more tools are required and internally decides which tools to call and in which order.
   * If a Reasoning Glimpse or plan pattern is present, tool usage is mapped to specific steps (“Step 2: Retrieve opportunity data from CRM”).

2. **Tool discovery and pre-run indication**

   * Before executing risky or long-running calls, the UI may show a brief, anticipatory indicator such as:

     * “Will search internal knowledge base and analytics warehouse.”
     * “Will contact CRM and Support ticketing systems (read-only).”
   * This is particularly important for new or sensitive capabilities, giving stakeholders a chance to cancel or adjust scope before tool calls begin.

3. **Tool call initiation**

   * For each active tool, a Tool Call Indicator appears in the inline Activity section, usually within a few hundred milliseconds of initiation.
   * The indicator shows:

     * Tool identity (icon + name).
     * Operation (“Searching…”, “Fetching…”, “Updating…”).
     * Initial status (“In progress”).

4. **Live execution and progress updates**

   * While the call is running, the indicator:

     * Displays a small animated element (e.g., spinner, shimmer, pulsing icon) to signal progress.
     * Optionally shows intermediate counts or milestones (“Scanning 1,200 transactions…”, “3 of 5 reports processed…”).
   * For multi-tool workflows:

     * Indicators may stack vertically, grouped by phase or tool type.
     * Aggregate labels summarize overall state (“2 tools running, 1 waiting for approval”).

5. **User control and intervention**

   * If the tool operation is cancellable, a “Cancel” or “Stop” control is available during execution.
   * For long-running read operations, a “Skip” control may allow the agent to proceed with partial data.
   * For write operations, indicators transition to an “Awaiting approval” state before committing:

     * “Preparing write to HR system (pending approval).”
     * Controls such as “Review 12 proposed changes” and “Approve all / Approve individually” are visible.
   * Changes to scope or approval status are reflected immediately in the indicator and any associated timeline.

6. **Completion**

   * On success, the indicator transitions to a stable “Completed” state:

     * Spinner or animated element stops.
     * Icon changes to a checkmark.
     * Label shifts to past tense: “Searched knowledge base (24 results found).”
   * The agent’s main answer incorporates tool outputs, and the Activity section clearly shows which tools contributed to the response.

7. **Failure and fallback**

   * On failure, the indicator shows:

     * A clear error status (“Failed”, “Timeout”, “Permission denied”).
     * A concise, non-technical explanation where possible.
     * Suggested actions (e.g., “Reconnect integration”, “Ask an admin”, “Retry with smaller date range”).
   * If the agent proceeds with degraded behavior (e.g., “Answering without CRM access”), that limitation is explicitly noted.

8. **Post-task visibility and audit trail**

   * All tool calls for a given task or session are recorded in the expanded timeline:

     * Timestamp, tool, operation, scope, status, duration.
   * The same information may be accessible later from an associated entity (record timeline, ticket history, assessment report), providing a durable audit trail.
   * Historical views remove continuous animations and emphasize static states and filters (“Show write operations only”, “Show failed calls”).

## States & Variants

### Depth Variants

* **Inline summary (default)**

  * Compact “Activity” section with one line per tool or per phase.
  * Shows tool name, operation, and status.
  * Minimal animation, suitable for everyday usage across B2B and B2C contexts.

* **Expanded activity log**

  * Detailed list or timeline of tool calls under the message or in a side panel.
  * Includes scope, timestamps, and error messages.
  * Intended for power users, admins, and debugging, not always needed for every user.

* **Debug / developer view**

  * Restricted mode that surfaces more technical details:

    * Endpoints, query summaries, approximate payload size, correlation IDs, latency metrics.
  * Useful for engineers and operators but generally hidden from non-technical end users.

### Risk & Operation Variants

* **Read-only tools**

  * Searching, retrieving, aggregating, or analyzing data.
  * Indicators emphasize source and scope, for example:

    * “Reading from Data Warehouse (read-only).”

* **Write / side-effectful tools**

  * Creating, updating, deleting records, or triggering workflows.
  * Indicators emphasize risk and approval:

    * “Proposing updates to 17 CRM opportunities (review required).”
    * “Sending 24 emails to customers (drafts ready for approval).”

* **Simulation / sandbox tools**

  * Operations that simulate changes without affecting production systems.
  * Indicators emphasize safe mode:

    * “Simulating HR policy changes in sandbox (no live changes).”

## Visual & Content Guidelines

### Visual Design

* **Use consistent iconography for tool categories**

  * Data sources, communication tools, ticketing systems, code execution, and system-of-record tools should have distinct but coherent visual treatments.
  * Risky or write tools may use badges or subtle color accents (e.g., a shield or pencil icon) to signal modification.

* **Show state changes clearly**

  * Avoid relying solely on animation. Combine:

    * Text status (“In progress”, “Completed”, “Failed”),
    * Icon state (spinner → check → warning),
    * Subtle color changes.

* **Limit concurrent motion**

  * When many tools run in parallel, animate the most relevant or active calls and keep others static.
  * Respect user and system preferences for reduced motion.

* **Align with existing design system components**

  * Reuse badges, pills, progress bars, accordions, and timelines defined in the product’s design system.
  * Introduce a minimal set of new tokens for tool-specific states (icons, colors, motion).

### Content & Labeling

* **Prefer domain language over internal jargon**

  * “Sales CRM” or “Customer database” is usually clearer than “sfdc-api” or “psql-prod-4”.
  * “Reading account records” communicates intent better than “GET /accounts”.

* **Make read vs write explicit**

  * Use verbs that clearly distinguish reads from writes:

    * Read: “Searching”, “Fetching”, “Reading”, “Analyzing”.
    * Write: “Updating”, “Creating”, “Deleting”, “Sending”.
  * Add qualifiers for risky operations:

    * “Updating (pending approval)”.
    * “Deleting (requires admin approval)”.

* **Include scope where helpful**

  * Indicate the size or subset of data being touched:

    * “Reading 12 invoices from last month.”
    * “Preparing updates for 3 at-risk contracts.”

* **Avoid overpromising**

  * Do not claim that tools are being used when the agent is replying purely from the model, and vice versa.
  * If a tool is unavailable and the agent falls back to model-only behavior, state that limitation clearly.

* **Handle partial or degraded states explicitly**

  * If a subset of tools fails, explain the resulting limitations:

    * “CRM was unavailable; answer is based on ticket history only.”

## Data, Privacy & Security Considerations

* **Minimize exposure of sensitive details in labels**

  * Avoid including personally identifiable information or secrets in tool labels or descriptions.
  * Prefer aggregate or abstract descriptions:

    * “Analyzing 45 payroll records” instead of listing names or IDs.

* **Respect access control boundaries**

  * Tool usage indicators must not leak the existence of restricted data or systems to unauthorized users.
  * When an agent cannot access a system, use generic wording:

    * “Some records were inaccessible due to permissions.”

* **Separate what was accessed from what was changed**

  * Make it clear which tools were read-only and which performed changes.
  * In audit views, structure logs with clear sections: “Data accessed” vs “Actions taken”.

* **Align tool usage logging with compliance policies**

  * Treat tool usage logs as sensitive operational data. Apply appropriate retention, masking, and access control policies.
  * Provide controls for exporting or reviewing logs only to authorized roles (e.g., admins, auditors).

* **Clarify environment and scope**

  * Always indicate when actions occur in sandbox vs production environments, reducing accidental misconceptions about impact.
  * For multi-tenant platforms, avoid cross-tenant leakage in labels and logs.

## Interaction Patterns

### Pre-Execution Confirmation for Risky Tools

* Before executing write operations, display tool indicators in a “pending” state with clear controls:

  * “Review details” → opens a diff or summary.
  * “Approve all” or “Approve individually” for batch writes.
  * “Reject” or “Cancel” to abort the action.
* The agent’s language should clarify that proposed changes have not yet been applied.

### Mid-Run Steering

* For complex or long-running tasks, allow mid-run adjustments:

  * Limiting scope (“Only update deals over $50k.”).
  * Switching environment (“Run this in sandbox first.”).
  * Pausing specific tool calls while others proceed.
* Changes to configuration should be reflected immediately in corresponding Tool Call Indicators and the activity timeline.

### Post-Execution Review

* After completion, provide:

  * A concise summary of tool actions in the chat context (“Updated 7 opportunities and created 3 follow-up tasks.”).
  * A link or inline expansion to view the full tool usage log or diffs.
* This pattern is particularly important where manual review is part of standard operating procedures (e.g., finance, compliance).

### Error Handling and Recovery

* When a tool fails:

  * Clearly mark the indicator with a failure state and short explanation.
  * Offer recovery actions where appropriate (“Retry”, “Try a smaller date range”, “Reconnect integration”).
  * Indicate downstream effects (e.g., “Will continue without analytics data; results may be incomplete.”).

## Example Use Cases

### Sales & Revenue Operations Copilot

A sales manager requests:

> “Prioritize this quarter’s pipeline, flag deals at risk, and update stages for those unlikely to close.”

Tool Usage Indicators show:

* “Reading opportunity data from Sales CRM (read-only)…”
* “Analyzing win probability model results…”
* “Preparing updates to 23 opportunities (pending approval)…”
* “Creating 5 follow-up tasks in Support system (pending approval)….”

The manager reviews the proposed changes, approves them, and the indicators transition to “Completed”. The activity timeline provides an audit trail for revenue operations and compliance teams.

### HR & People Ops Assistant

An HR partner asks:

> “Generate a list of employees eligible for promotion, based on tenure, performance ratings, and role level, and create draft promotion cases in the HR system.”

Indicators show:

* “Fetching employee data from HR system (read-only)…”
* “Cross-checking performance reviews from the last 2 cycles…”
* “Drafting 14 promotion cases in HR system (pending approval)….”

Before creation, the assistant surfaces a structured review UI. Only after explicit confirmation do the indicators move from “pending” to “completed”.

### Analytics & BI Agent

A data analyst requests:

> “Investigate why infrastructure costs spiked in Q3 in the EU region and summarize top drivers.”

Indicators show:

* “Running SQL query on Cost ledger (read-only)…”
* “Joining Cost ledger with Deployment logs (read-only)…”
* “Running anomaly detection model on Q2–Q3 series…”

All operations are read-only. The activity section clearly signals that no changes are being made to production systems, reducing anxiety about unintended side effects.

### Customer Support Copilot

A support leader asks:

> “Identify customers who opened more than 10 tickets in the last 30 days and create follow-up cases for account management.”

Tool Usage Indicators show:

* “Searching ticket history in Helpdesk system (read-only)…”
* “Grouping tickets by customer account…”
* “Creating 32 follow-up cases in CRM (pending approval)….”

The leader can inspect which accounts will be affected and modify thresholds before approving, with each action visible in the activity timeline.

## Anti-Patterns & Pitfalls

* **Generic, opaque “thinking” states for tool actions**
  Using a single spinner or typing indicator for all activity, including tool calls, hides important information about data access and side effects.

* **Silent writes and hidden side effects**
  Performing system-of-record updates or sending messages without clearly labeled indicators and approval steps erodes trust and can cause real harm.

* **Overly technical labels**
  Surfacing internal endpoint names, table names, or job IDs as user-facing labels (“POST /api/v2/records”) increases cognitive load and confuses non-technical users.

* **Excessive verbosity by default**
  Showing every micro-call or low-level event (e.g., multiple paginated fetches) in the main chat view overwhelms the interface. Detailed logs belong behind an expanded or debug view.

* **Inconsistent treatment across surfaces**
  If some tools or agents surface indicators while others with similar risk profiles do not, users cannot reliably predict impact. Tool usage transparency should be coherent across the product.

* **Misaligned labels and behavior**
  Labeling a tool as “read-only” when it can write, or failing to update indicators when a tool fails or is skipped, quickly undermines the pattern’s purpose.

## Metrics & Evaluation

To evaluate the effectiveness of Tool Usage Indicators, consider:

* **Trust & perceived safety**

  * Changes in user-reported trust around data handling and system changes.
  * Reduction in “surprise” reports about unexpected changes or side effects.
  * Qualitative feedback from interviews and support tickets regarding clarity of tool behavior.

* **Operational safety**

  * Frequency and severity of incidents related to unintended writes or misdirected actions.
  * Number of write operations executed without manual approval, where approval is expected.
  * Rate of cancellations or scope reductions after users see tool indicators, indicating that visibility is catching mis-scoped operations.

* **Task success & efficiency**

  * Time to complete complex, tool-heavy tasks before vs after introducing indicators.
  * Reduction in rework caused by misunderstandings about data sources or scope.
  * Patterns in how often tool logs are consulted when troubleshooting issues.

* **Adoption and confidence in automation**

  * Adoption rate of higher-autonomy features (e.g., “auto-apply safe changes”) after introducing clearer tool visibility.
  * Differences in behavior between users who frequently inspect tool usage and those who do not.

## Implementation Notes

* **Represent tool calls as structured events**

  * Internally, model each tool call as an event with fields such as:

    * Tool identifier and category,
    * Operation type (read / write / simulate),
    * Status (queued, running, awaiting approval, completed, failed),
    * Scope (counts, filters, entities),
    * Time metadata and correlation IDs.
  * This makes it straightforward to render consistent indicators and logs across multiple surfaces.

* **Separate orchestration logic from UI rendering**

  * The orchestrator (e.g., agent framework, workflow engine) should emit tool call events with lifecycle updates.
  * The UI layer subscribes to these events and updates indicators accordingly, ensuring that visual state matches real execution state.

* **Integrate with Reasoning Glimpse or plan views**

  * For each reasoning step, associate tool events as children in a tree or graph structure.
  * In the UI, show high-level reasoning steps and annotate them with tool badges (e.g., “Used CRM” or “Used Analytics Warehouse”), with optional expansion for detailed calls.

* **Design for progressive disclosure**

  * Default to a minimal, readable inline Activity section.
  * Offer deeper inspection views (side panels, timelines) only when needed, such as in enterprise or debug contexts.
  * Ensure that minimal views still distinguish between read-only and write operations.

* **Instrument logs for observability and monitoring**

  * Store tool usage logs centrally for analysis and anomaly detection.
  * Track patterns such as:

    * Unusually high write volumes,
    * Tools failing frequently,
    * Calls against unexpected systems.
  * Use this data to refine guardrails, approvals, and the design of indicators.

* **Align with governance and role-based access**

  * Gate certain capabilities (viewing detailed logs, approving changes, running high-risk tools) behind roles and permissions.
  * Ensure indicators respect those boundaries: some users may see only high-level labels, while admins see more detailed activity.

By following this pattern, AI-enabled applications can communicate exactly how agents interact with tools and systems, making behavior more predictable, controllable, and auditable—especially in B2B and B2C environments where data integrity and trust are critical.
