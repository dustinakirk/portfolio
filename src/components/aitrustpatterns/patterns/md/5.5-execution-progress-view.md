# 5.5 Execution Progress View

Visualizes an AI agent’s multi-step plan and current execution state so that users understand what is happening, how far along it is, and where intervention is needed.

*Last updated December 2025*

---

## Overview

Execution Progress View is a structured visualization of an AI agent’s work as it executes a plan. It typically appears as a step-based tracker and progress indicator embedded in, or adjacent to, an agent conversation. The pattern exposes the plan, highlights the current step, distinguishes completed and upcoming steps, and surfaces blockers that require attention.

The primary value is reduced uncertainty. Instead of a generic “Working…” indicator, users see *what* the system is doing, *where* it is in the workflow, and *how* that maps to their business process. This improves perceived reliability, reduces premature cancellations and duplicate requests, and makes it safer to delegate high‑impact tasks to agentic systems.

**Example concept**

An incident-investigation assistant called **Atlas** runs a 5‑step analysis plan:

1. Scope investigation
2. Pull metrics & error rates
3. Correlate patterns
4. Draft root cause findings
5. Validate confidence levels

During execution, the chat shows a vertical stepper with checkmarks for finished steps, a highlighted state for the active one (“Correlate patterns”), and muted icons for upcoming steps. Below, a horizontal progress bar labeled “Step 3 of 4 – Correlation analyst processing…” fills as work proceeds, with a clear percentage and controls to **Pause** or **Show details**. If the agent gets stuck (for example, missing datastore credentials), the active step switches to a “Blocked” state with a short explanation and a quick action to resolve it.

---

## Problem

Without an explicit execution view, agentic workflows often feel opaque and unpredictable:

* The interface shows only a spinner or vague status (“Thinking…”, “Working on it”), leaving users unsure whether the system is stuck, idle, or progressing normally.
* Long-running or multi-step tasks provide no visibility into which tasks have completed, which are in progress, and how much work remains.
* When something goes wrong (for example, missing access, inconsistent inputs, API rate limits), the system fails silently or returns a generic error, forcing users to guess what needs to be fixed.

Execution Progress View addresses this by making the agent’s plan, state, and blockers visible in a compact, always-available surface.

---

## When to Use This Pattern

* Agentic workflows that involve **multiple sequential or parallel steps**, such as investigations, analysis pipelines, content workflows, or configuration changes.
* **Long-running tasks** where execution time is measured in tens of seconds or minutes, and uncertainty can cause mistrust or duplicate requests.
* **High‑risk or high‑impact operations**, such as deployments, data migrations, security scans, or bulk updates, where stakeholders must understand what the agent is doing.
* **Multi-agent systems** where different specialized agents handle stages of the workflow and responsibility needs to be explicit.
* Scenarios where **human intervention may be required mid-run** (approvals, credentials, policy checks, additional inputs).

## Probably Overkill When...

* Simple, single-step actions complete in a couple of seconds and are already clearly reflected in the UI (for example, formatting a short text snippet).
* The main application view already conveys progress unambiguously (for example, a file finishes uploading and appears immediately in a list).
* Agent behavior is stateless or ephemeral, and there is no meaningful notion of a multi-step plan or pipeline.
* The workflow has no user-facing notion of “steps,” and adding one would create unnecessary complexity.

---

## Pattern Anatomy

Execution Progress View is typically composed of a **step-based tracker** plus **real-time status indicators**, integrated into the agent’s conversation stream or a dedicated side panel.

### Entry Points

* **Primary**: Within the chat conversation, grouped with the agent’s message that describes the plan or confirms that execution has started.
* **Secondary**: A persistent panel or drawer attached to the main content area (for example, right rail in a dashboard, bottom execution console in a builder).
* **Contextual**: Inline indicators in related surfaces, such as:

  * A toast or banner summarizing “Run 3 of 5: ‘Marketing pipeline setup’ in progress”.
  * Badges on navigation or tabs showing active runs (“1 running”, “2 blocked”).

### Core Item / Object

The core unit in this pattern is an **execution step** within an **agent-run**.

For each step:

* **Label**
  Short, action-oriented phrase that describes the outcome, e.g., “Pull metrics & error rates”, “Generate remediation plan”, “Sync changes to staging cluster”.

* **Description / statement**
  Optional explanatory text clarifying what the step includes, assumptions, or scope, e.g., “Querying last 24 hours of error logs across services tagged ‘checkout’”.

* **Controls**
  Depending on risk and complexity:

  * Pause / resume entire run or this step.
  * Cancel run.
  * Retry step.
  * Skip step (where safe and well‑guarded).
  * “Fix” or “Provide input” when blocked.

* **Optional metadata**

  * Status: Not started, In progress, Completed, Blocked, Failed, Skipped.
  * Responsible agent or role: “Metrics Agent”, “SQL Analyst”, “Orchestration Agent”.
  * Time estimates or elapsed time.
  * Link to logs or detailed traces.
  * Impact scope tags: environments, datasets, segments.

The **run container** aggregates these steps and may display:

* Run title and description.
* Overall status (“Running”, “Blocked”, “Completed with warnings”).
* Overall progress indicator (percentage, step count).
* Global controls and links to history.

### Behavior & Lifecycle

1. **Plan generation**

   * The agent proposes a structured plan, often as a numbered list or stepper.
   * The initial state shows all steps as “Not started” or lightly muted.

2. **Optional plan confirmation**

   * For higher-risk operations, the system may require an explicit confirmation before starting (“Confirm and run 5‑step investigation”).
   * Users can edit, reorder, or deselect steps where supported.

3. **Execution start**

   * The first active steps transition to “In progress” (for parallel execution, multiple steps highlight simultaneously).
   * A system message indicates that execution has started, often with a timestamp.

4. **Progress updates**

   * As tasks complete, steps switch to “Completed” with checkmarks and timestamps.
   * The active step(s) remain visually distinct via color, dot, glow, or motion.
   * A progress bar and/or compact “Step X of Y” indicator summarises current position in the sequence.

5. **Parallel branches**

   * When several steps run concurrently, the view either:

     * Shows them at the same level with multiple “In progress” indicators, or
     * Groups them under a collapsible “Batch” or “Subflow” node (for example, “Enrich 12 data sources (4/12 complete)”).

6. **Blocked / attention-required states**

   * If execution encounters a recoverable issue (permissions, missing data, conflicting instructions), the affected step flags as “Blocked”.
   * A short inline explanation and a clear call to action appear, e.g.,

     * “Blocked: missing Git credentials. Connect repository.”
     * “Blocked: approval required to update production environment. View changes.”
   * While blocked, the run either pauses globally or continues with independent steps, depending on orchestration rules.

7. **Error handling and retries**

   * Failures that cannot proceed automatically are clearly marked with an error icon and summary.
   * Optional controls allow retrying the step with the same or adjusted inputs.
   * If the overall run is marked as “Failed” or “Completed with errors”, the execution view highlights problematic steps first.

8. **Completion and handoff**

   * When all required steps reach a terminal state (Completed, Skipped, or Irreversibly Failed), the overall run state updates to “Completed” or “Completed with warnings”.
   * The agent presents a summary and any resulting artifacts (reports, configuration diffs, generated content).
   * The progress tracker remains available as a historical record, often collapsible or accessible from a “Run details” page.

9. **History and re‑entry**

   * Past runs can be revisited from activity logs, case records, or project views.
   * The same execution view pattern, now read-only, helps auditors or collaborators understand what occurred and when.

---

## States & Visual Language

A consistent state model is critical to comprehension:

* **Not started** – Muted or low-contrast, no icon fill.
* **In progress** – Highlighted step with active indicator (dot, spinner, pulse).
* **Completed** – Checkmark or success icon, strong contrast label, timestamp.
* **Blocked** – Warning icon and color, inline reason, prominent “Fix” or “Review” action.
* **Failed** – Error icon and color, link to details and logs.
* **Skipped** – Greyed-out with clear label to avoid confusion with errors.

Design considerations:

* Rely on **more than color** to encode state (icons, shapes, labels) for accessibility.
* Keep the number of simultaneous states visible manageable; group or collapse distant or low‑relevance steps.
* Avoid overly precise or misleading percentages; coarse milestones often better reflect reality for AI workflows.

---

## Multi-Agent Considerations

In multi-agent systems, several agents may contribute to a single run:

* **Agent attribution per step**

  * Display the responsible agent’s name, role, or avatar on each step (“Metrics Agent”, “LLM Writer”, “Approval Orchestrator”).
  * For shared steps, show multiple avatars or a “handoff” indicator.

* **Cross-agent handoffs**

  * Explicitly show transitions where ownership changes, for example:

    * “Analysis Agent → Drafting Agent → Reviewer Agent”.
  * Use these transitions as natural places to request approvals or additional inputs.

* **Concurrency and orchestration**

  * When multiple agents work in parallel, consider grouping their steps under a parent node (for example, “Specialist agents running (3/5 complete)”).
  * The overall progress view should remain comprehensible even if many internal micro-steps exist; surface only meaningful milestones.

---

## Interaction Design & Controls

Execution Progress View often pairs visualization with critical controls:

* **Pause / resume**

  * Suitable for longer runs with potential side effects.
  * When paused, clearly indicate the frozen state and which steps are waiting.

* **Cancel run**

  * Provide a safe way to stop execution, with confirmation text that clarifies consequences (“No changes will be applied to production”).
  * Show whether cancellation is immediate or “best effort”.

* **Fix / unblock actions**

  * Present short, focused flows for resolving blockers: connecting an integration, adding credentials, adjusting filters, or granting temporary permissions.
  * Return users directly to the execution view afterward, with the step resuming or retrying automatically.

* **View details / logs**

  * Offer an expandable panel or “Show details” link for deeper technical information: prompts, queries, API calls, system messages.
  * Default to a concise view to prevent overwhelming non-technical users.

* **Run-level actions**

  * Duplicate plan, rerun with new parameters, schedule run, or share a link to the run for collaboration.

Interaction richness should scale with risk and complexity: critical production operations justify more controls; low-risk generative tasks may require only simple status and cancellation.

---

## Content Guidelines

* **Lead with outcomes, not mechanics**

  * Step labels should describe the business outcome (“Validate confidence levels”) rather than internal implementation (“Run model X on dataset Y”).

* **Use consistent verb structures**

  * For example, start steps with action verbs: “Gather…”, “Analyze…”, “Generate…”, “Apply…”.

* **Explain blockers in plain language**

  * Combine a short high-level description with concise technical hints, e.g., “Blocked: cannot access S3 bucket ‘events-prod’. The configured role lacks `s3:GetObject` permissions.”

* **Manage expectations for duration**

  * Where possible, provide qualitative guidance: “Usually completes in under 2 minutes.”
  * Avoid promising exact times that the system cannot reliably meet.

* **Align terminology with the surrounding domain**

  * For a marketing platform, use “campaign”, “segment”, “send list”; for observability, use “services”, “spans”, “error rate”.

---

## Accessibility & Internationalization

* Use semantic markup for lists, progress indicators, and statuses (for example, `aria-live` for status updates, `role="progressbar"` with proper attributes).
* Ensure that icons and colors are supplemented with text labels and patterns suitable for color-blind users.
* Announce key state changes for assistive technologies (“Step 3 of 5 started: Correlate patterns”).
* Plan for label length variability across languages; step containers should gracefully support longer translated text without truncating critical meaning.
* Avoid encoding state purely through animation; any motion should be subtle and paired with static indicators.

---

## Implementation Notes

* **Data model**

  * Represent runs and steps with explicit IDs, ordered positions, states, timestamps, and responsible agents.
  * Allow partial updates so that the UI can incrementally update as events stream in.

* **Real-time updates**

  * Use websockets, server-sent events, or polling to keep progress live.
  * Handle disconnects gracefully by resyncing state when the page regains focus or reconnects.

* **Idempotency and resilience**

  * Ensure that reloading the page or navigating away temporarily does not lose track of a run; users should be able to re-open the same execution view from history.

* **Security & privacy**

  * Logs and “Show details” views may expose prompts, data samples, or system metadata; apply appropriate redaction and access controls.
  * Blockers that involve sensitive information (for example, credentials) should route to secure input flows.

* **Performance considerations**

  * For very long pipelines, consider virtualized lists and summarized nodes (“+15 more steps”) with drill-down options.
  * Avoid UI thrashing; batch rapid-fire updates into coherent changes.

---

## Metrics & Evaluation

Success of this pattern can be tracked through:

* **Behavioral indicators**

  * Reduction in cancelled runs due to perceived “stuck” behavior.
  * Fewer duplicate requests or re-submissions for the same task.
  * Increased completion rates for long-running or complex workflows.
  * Frequency and resolution time of “Blocked” states.

* **Support and qualitative signals**

  * Decrease in support tickets or feedback mentioning confusion about what the agent is doing.
  * Positive mentions of clarity, transparency, and predictability in user interviews or surveys.

* **Engagement with transparency features**

  * Click-through rates on “Show details”, “View logs”, or per-step explanations.
  * Adoption of shared run links among collaborators.

---

## Common Pitfalls & Anti-Patterns

* **Fake or misleading progress**

  * Showing smooth, linear progress when the system has no real notion of progress erodes trust once users notice inconsistencies.

* **Overwhelming detail by default**

  * Surfacing every micro-action, prompt, or API call in the main view makes the pattern noisy and hard to scan.

* **Ambiguous labels**

  * Vague terms such as “Step 3: Processing” do not convey meaningful value; each step should map to a user-understandable outcome.

* **Silent failure or hidden blockers**

  * Failing without clearly marking the affected step or explaining how to resolve the issue leads to frustration and re-runs.

* **Non‑responsive controls**

  * Pause, cancel, and retry actions must update the UI immediately with transitional states (“Cancelling…”) to avoid rapid repeated clicks and race conditions.

## Example Use Cases

* **Data & analytics platforms**

  * A pipeline-building agent shows ingestion, transformation, validation, and publishing stages, indicating which data sources and models are being touched.

* **Observability & incident response**

  * An investigation agent runs scoped queries, correlates metrics and traces, identifies probable root causes, drafts a postmortem outline, and prepares remediation tasks.

* **DevOps & deployment tools**

  * An AI deployment orchestrator shows build, test, canary rollout, traffic shifting, and rollback checks as distinct steps, highlighting approvals needed for production.

* **Marketing, sales, and CRM automation**

  * A campaign agent builds segments, drafts messages, runs compliance checks, schedules sends, and creates follow-up experiments, with an explicit progress view for each stage.

* **Knowledge management and content operations**

  * A documentation agent crawls sources, extracts entities, generates drafts, requests human review, and publishes updates, with clear blockers where manual sign-off is required.

---

## Related Patterns

* **Plan Preview** – Shows the proposed multi-step plan before execution starts, often feeding directly into the Execution Progress View once confirmed.
* **Safeguarded High-Risk Actions** – Adds confirmations, reviews, and approval gates around sensitive steps within the execution flow.
* **Explanatory System Messages** – Provides natural-language explanations of what the agent is doing and why, complementing the visual stepper.
* **Run History & Audit Trail** – Extends the execution view into long-term records for compliance, collaboration, and debugging.

These patterns together create a comprehensive transparency framework that increases trust in agentic AI systems operating within complex business workflows.
