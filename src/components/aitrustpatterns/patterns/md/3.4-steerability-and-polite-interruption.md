# 3.4 Steerability & Polite Interruption

Enables users to redirect an agentic AI mid-task, preserving useful progress while clearly acknowledging and incorporating new intent.

*Last updated December 2025*

---

## Overview

Steerability and polite interruption refer to the system’s ability to accept mid-stream changes in direction, integrate them into the agent’s current plan, and continue work without unnecessary reset or loss of context.

In agentic AI experiences, especially those driven by natural language chat, users expect conversational flexibility: it should be possible to correct misunderstandings early, add new constraints, pivot the objective, or stop unsafe or undesired actions without starting from scratch.

This pattern defines how the agent detects and responds to interruptions (both explicit and implicit), how it adjusts its plan, and how it communicates status back to the user in a calm, trustworthy manner.

> **Example concept (for an interactive demo)**
> A multi-step “Campaign Builder Copilot” is creating an email drip sequence. While the agent is outlining Step 3, the user types:
> “Actually, make this campaign SMS-first for EMEA only and drop any discounts.”
> The UI briefly shows “Revising plan…”; the agent pauses the current step, updates the plan summary, visually highlights which steps changed (channels and regions), and then resumes generating content with the new constraints. Previous draft steps remain available in an “Earlier version” drawer for reference or rollback.

---

## Problem

Without steerability and polite interruption:

* Long-running or multi-step AI workflows feel brittle; a small change in intent often forces a complete restart or manual reconfiguration.
* Users experience anxiety and mistrust when they cannot see whether a critical mid-task correction (e.g., “do not email this customer segment”) has actually been applied.
* The system’s behavior feels unlike human collaboration; conversation flows become linear scripts instead of flexible dialogues, which makes agentic AI feel more like an opaque batch process than a partner.

This pattern ensures that agentic systems stay responsive to evolving intent, reduce wasted effort, and maintain user confidence that the agent is truly listening and adapting.

---

## When to Use This Pattern

* **Multi-step or long-running tasks**
  For workflows like report generation, campaign building, coding and deployment, data remediation, or workflow automation where the agent executes a sequence of steps over time.

* **Evolving or ambiguous goals**
  When initial instructions are incomplete, exploratory, or likely to change as the user sees interim results (e.g., research assistance, creative work, “help me explore options”).

* **High-stakes or policy-heavy contexts**
  In domains such as finance, security operations, legal review, medical documentation, or HR where mid-task corrections and constraints (e.g., compliance rules) must be honored immediately.

* **Agent-driven orchestration over external systems**
  When agents trigger actions in third-party tools (CRM, marketing platforms, cloud infrastructure, ticketing, etc.), and users must retain fine-grained control and the ability to halt or redirect.

## Probably Overkill When...

* **Single-turn Q&A or simple transformations**
  For basic question answering or one-off text transformations, a standard “edit and resend” affordance usually suffices.

* **Highly structured wizards with narrow scope**
  When a workflow is short, linear, and fully controlled by a form or wizard, inline form edits are often simpler than agent-level steerability.

* **Non-critical, low-effort tasks**
  For casual tasks where re-running is trivial and consequences are low (e.g., generating a fun tagline), elaborate interruption handling may add unnecessary complexity.

## Pattern Anatomy

This pattern lives primarily inside the conversational and “agent run” surfaces: where the agent’s plan, status, and artifacts are visible, and where the user can intervene.

### Entry Points

* **Primary entry point: active run in the chat surface**

  * While the agent is “thinking”, streaming, or executing steps, the message composer remains active.
  * Inline controls such as **Pause**, **Stop**, **Adjust**, or **Revise plan** appear adjacent to the current run or plan card.

* **Secondary entry point: plan summary / task panel**

  * A collapsible panel or card summarizing the current plan (e.g., “Steps 1–5”) includes controls like **Edit constraints**, **Skip step**, or **Change target** that trigger steering flows.

* **Contextual entry points**

  * Lightweight prompts such as “Need to change direction?” or “Update constraints” appear after major milestones, errors, or when the agent detects conflicting instructions.
  * System notifications or toasts (e.g., “Plan updated to exclude blocked regions”) provide quick access to see and adjust the new plan.

### Core Item / Object

The core object is a **steerable agent run**: a single goal-directed execution with an attached plan, status, artifacts, and control affordances.

Typical structure:

* **Label**

  * A concise title expressing the goal, often derived from the user’s initial instruction.
  * Examples: “Optimize Q4 ad campaign”, “Refactor data ingestion pipeline”, “Summarize customer feedback for Product A”.

* **Description / statement**

  * A short description of the current plan or scope, updated when steering occurs.
  * Includes key constraints (“Region: EMEA”, “Channel: SMS only”, “Exclude PII fields”).

* **Controls**

  * Inline actions such as:

    * **Pause / Resume**
    * **Stop / Cancel**
    * **Revise plan** (update constraints, objectives, or assumptions)
    * **Undo last change** or **Restore earlier plan**
    * **Open logs** or **View steps** (to inspect reasoning and execution status)

* **Optional metadata**

  * Status: *Planning*, *Executing*, *Paused*, *Awaiting input*, *Revising plan*, *Completed*, *Failed*.
  * Scope / impact: affected environments, datasets, accounts, or user segments.
  * Risk level or approvals: whether certain changes require confirmation or elevated permissions.
  * Timestamps and run IDs for traceability.

### Behavior & Lifecycle

A typical lifecycle:

1. **Initial intent and plan creation**

   * The user expresses a goal in natural language.
   * The agent synthesizes a plan (steps, dependencies, outputs) and presents a concise summary before or during execution.

2. **Execution begins**

   * The agent starts acting (e.g., drafting, querying APIs, updating configurations).
   * The UI indicates live progress and keeps the composer and controls available.

3. **Interruption or steering input occurs**

   * The user sends a message that contradicts, refines, or pivots the goal, or presses an explicit control (Pause / Adjust / Stop).
   * The system treats this as a high-priority signal, even if it arrives mid-stream.

4. **Immediate acknowledgment and safe pause**

   * The agent stops further non-essential actions as quickly as possible and responds promptly with an acknowledgment.
   * The response restates the detected change (e.g., “Understood. Updating the plan to only target EMEA and remove discount offers.”).
   * For high-risk actions, any pending side effects are held until clarification is resolved.

5. **Reconciliation and plan adaptation**

   * The agent re-evaluates the existing plan and determines what can be reused versus what must be updated or discarded.
   * The previous plan is archived or versioned; the new plan highlights what changed (e.g., step markers or diff-style visual cues).

6. **Presenting the updated plan**

   * The revised plan is shown succinctly, emphasizing new constraints or altered steps.
   * For high-stakes workflows, the system may request confirmation (“Proceed with updated plan?”).
   * For low-stakes tasks, the plan may simply update and proceed, with an option to roll back.

7. **Resumption of execution**

   * Once confirmed (implicitly or explicitly), the agent resumes from the appropriate step with the new constraints.
   * Existing useful work is reused (e.g., earlier drafts, cached results), avoiding unnecessary repetition.

8. **Handling repeated or overlapping interruptions**

   * Subsequent steering inputs are queued or merged in a controlled manner.
   * The UI may summarize multiple adjustments (“Three changes applied: region, budget, and channel.”) rather than replaying full plans each time.

9. **Completion and review**

   * At the end of the run, the plan history shows major redirections and the rationale for key decisions.
   * The user can inspect what was executed under each version of the plan for traceability and learning.

## Implementation Guidance

### Detection and Classification of Interruptions

* **Input-based detection**

  * Treat any new message while a run is active as a potential steering event.
  * Classify the message into categories such as *clarification*, *constraint update*, *goal pivot*, *stop/cancel*, or *out-of-band chit-chat* using intent recognition.

* **Control-based detection**

  * Observe explicit control triggers (Pause, Stop, Adjust, Undo) as authoritative interruptions that should preempt the normal agent loop.

* **Priority and routing**

  * Ensure that interruption signals are routed to the agent orchestrator with higher priority than ongoing tool calls or streaming content so that side effects can be halted or minimized quickly.

### State Management and Plan Adaptation

* **Stateful context per run**

  * Maintain a structured representation of the plan (e.g., task graph or structured JSON) separate from free-text chat.
  * Track completed, in-progress, and pending subtasks, along with dependencies and any external effects (e.g., “tickets created”, “instances modified”).

* **Non-destructive updates**

  * Version plans instead of overwriting in place.
  * When a steering input arrives, compute a “delta plan”: what steps remain valid, what must be altered, and what should be skipped.

* **Selective rollback**

  * For operations that have already affected external systems, provide remediation options (e.g., revert configuration, close created tickets) where feasible.
  * Make clear which changes can be undone and which are permanent or require manual intervention.

### Conversation & UX Patterns

* **Immediate, concise acknowledgment**

  * Always follow an interruption with a quick confirmation that the agent has heard and understood the change.
  * Restating the new intent or constraint builds trust and reduces ambiguity.

* **Short, visible re-planning phase**

  * Use transient status indicators such as “Revising plan…” rather than long, silent delays.
  * Keep the re-planning explanation brief while offering expandable details for advanced users.

* **Contextual, non-intrusive system messages**

  * When a change is substantial (e.g., switching environments or targets), call attention to it once, then respect the updated direction without repeatedly asking for confirmation.

### Safety and Policy Integration

* **Safety first on redirects**

  * Steerability must not allow users to bypass safety rules or policy checks.
  * If a redirection conflicts with safety constraints, the agent should explain what cannot be done and propose compliant alternatives.

* **Guarding against conflicting instructions**

  * Detect contradictions (e.g., “send to all customers” after “exclude EU customers” when GDPR constraints exist) and surface them clearly.
  * Prefer a short clarification turn over silently picking one interpretation.

* **Access control and approvals**

  * For sensitive actions, connect interruption handling with role-based checks and approval flows (e.g., require admin confirmation before re-running destructive tasks under new parameters).

### Technical Considerations

* Cancellation and cooperative interruption in long-running tasks (e.g., cancelable async operations, tool calls, and streaming responses).
* Logging and observability for each interruption, including timestamps, changed parameters, and affected outputs.
* Resilience to network interruptions and reconnect scenarios (e.g., resuming a paused run after a user returns).

## Use Cases

### Content & Communication

* **Email and message drafting**

  * While the agent drafts a sequence of emails, the user adds mid-run: “Make the tone more formal and remove any discount language.”
  * The agent updates its style and constraints without discarding already useful structure or subject lines.

* **Knowledge articles and documentation**

  * During document generation, the user interrupts to narrow the audience (“Assume an internal engineering audience, not customers.”), and the agent revises the outline and subsequent content accordingly.

### Research & Analysis

* **Market or competitive research**

  * As the agent compiles a multi-part report, the user introduces new constraints (“Exclude sources older than 12 months; focus on North America.”).
  * The agent pauses, filters previous findings, and resumes with updated criteria.

* **Data diagnostics and root-cause analysis**

  * While the agent analyzes logs or telemetry, the user specifies a different time range or subset (“Look only at the latest deployment.”).
  * The agent adapts queries and clearly explains which data is now in scope.

### Task Automation & Orchestration

* **Operations and DevOps agents**

  * An infrastructure copilot is preparing to scale resources. The user interrupts: “Limit changes to staging only.”
  * The agent halts production-related steps, updates the plan to staging scopes, and resumes.

* **Business workflow automation**

  * A CRM agent is bulk-updating accounts. Mid-run, the user adds a filter (“Only accounts with open opportunities above $50k.”).
  * The agent stops further updates, recalculates the target set, and requests confirmation for the new scope before continuing.

### Error Correction & Clarification

* **Model hallucination correction**

  * After spotting a factual error, the user replies immediately with the correct information.
  * The agent acknowledges the correction, updates its working context, and regenerates dependent outputs.

* **Constraint reinforcement**

  * When the agent suggests an action that violates company policy, the user reiterates the policy.
  * The agent apologizes, logs the constraint, and re-plans around it.

### Collaborative Ideation

* **Brainstorming with constraints**

  * During idea generation, the user steers with prompts such as “Focus on sustainability”, “Avoid ideas needing new legal approval”, or “Aim for low-cost experiments.”
  * The agent continues from the current state but changes its selection criteria and framing, preserving momentum.

## Interaction & Content Guidelines

### Acknowledgment & Tone

* Use clear, neutral language for acknowledgments:

  * “Understood. Updating the plan to…”
  * “Pausing current actions and revising based on…”
* Restate key elements of the new direction to reinforce understanding.
* Avoid language that blames the user or implies error; instead, treat redirection as a normal part of collaboration.

### Explaining Changes

* Summarize changes succinctly:

  * “Changes applied: 1) Channel set to SMS, 2) Region limited to EMEA, 3) Discounts removed.”
* Provide optional detail affordances (e.g., “View plan diff”) instead of forcing verbose explanations into the main conversation.

### Handling Conflicts and Limits

* When instructions conflict or cannot be honored:

  * Clearly state what is infeasible and why.
  * Offer one or more alternative paths.
  * Maintain a calm, professional tone and avoid ambiguous phrases like “might not work” without specifying constraints.

## Variants

### 1. Soft Steer (Micro-adjustments)

* Small changes that do not fundamentally alter the goal (e.g., tone, level of detail, format).
* Implementation:

  * Update generation parameters and prompts in-place.
  * No need for full plan re-approval; a short acknowledgment in the chat is sufficient.

### 2. Hard Redirect (Goal Change)

* A new instruction that effectively defines a new goal (e.g., from “create an email campaign” to “generate a data-driven performance analysis”).
* Implementation:

  * Offer to start a new run or thread while preserving the previous one.
  * Provide a clear boundary message: “This is a new task; the previous plan will remain available in the sidebar.”

### 3. Scoped Adjustment (Partial Plan Edit)

* Changes affecting only parts of the plan (e.g., “Skip step 3”, “Change only the onboarding emails for developers”).
* Implementation:

  * Present the affected steps, allow selective edits, and then recompute downstream dependencies.
  * Visual diff or strike-through for removed steps improves comprehension.

### 4. Explicit vs. Implicit Interruption

* **Explicit**: Buttons and commands such as “Pause”, “Stop”, “Update filters”.
* **Implicit**: Free-form messages that the system interprets as steering (“Actually, do not include interns.”).
* Both paths should converge on the same internal mechanisms for safety and consistency.

## Edge Cases & Pitfalls

* **Over-interruption leading to thrashing**

  * Users may change direction repeatedly, causing the agent to re-plan excessively.
  * Mitigation: summarize multiple changes, suggest stabilizing constraints, or recommend a brief alignment step.

* **Ambiguous steering instructions**

  * Commands like “fix this” or “make it better” can be unclear.
  * Mitigation: agent requests focused clarification rather than making high-risk guesses.

* **Partial application of constraints**

  * Risks arise when constraints apply only to later steps, leaving earlier artifacts inconsistent.
  * Mitigation: warn when earlier outputs are now outdated and offer regeneration options.

* **Silent failures to interrupt underlying tools**

  * Inability to cancel long-running external calls can undermine user expectations.
  * Mitigation: clearly state what can be halted immediately versus what will complete but be discarded.

* **Security and compliance regressions**

  * Careless plan updates might unintentionally drop important filters (e.g., removing compliance checks).
  * Mitigation: mark certain safeguards as non-removable; explain when requested changes conflict with policy.

## Metrics & Evaluation

To assess whether this pattern is functioning effectively:

* **Usage metrics**

  * Frequency and timing of interruptions per run.
  * Distribution of interruption types (clarifications, corrections, pivots, stops).

* **Outcome metrics**

  * Task completion rate before vs. after introducing steerability.
  * Reduction in “start over” events and repeated runs for similar goals.
  * Error or incident rates when agents act in external systems.

* **Experience metrics**

  * User-reported trust and perceived control (e.g., via in-product surveys after significant interruptions).
  * Qualitative feedback about whether mid-stream changes “stick” and feel respected.

* **Operational metrics**

  * Success rate of cancellation and rollback operations.
  * Latency between interruption and agent acknowledgment.

---

## Accessibility & Inclusivity Considerations

* Ensure all key controls (Pause, Stop, Adjust plan) are keyboard-accessible and properly labeled for assistive technologies.
* Use ARIA live regions to announce major state changes such as “Run paused”, “Plan updated”, or “Execution resumed”.
* Avoid overly dynamic or flashing indicators during re-planning; favor stable, minimal animations suitable for users with sensory sensitivities.
* Provide clear textual summaries instead of relying solely on color or icon changes to indicate status or plan diffs.

---

## Anti-Patterns

Avoid the following behaviors:

* **Ignoring or minimizing interruptions**

  * Continuing execution for several seconds without acknowledgment, especially for high-risk actions.

* **Discarding useful work without warning**

  * Completely resetting the task on every steering input without explaining what was lost.

* **Overly verbose or theatrical status updates**

  * Long, chatty explanations that obscure key changes and slow task completion.

* **Using interruptions to upsell or distract**

  * Injecting promotional or irrelevant content when users are attempting to regain control or correct the agent.

* **Allowing interruptions to bypass safety**

  * Treating user steering as permission to disable critical guardrails or policy checks.

---

## Checklist

Before shipping a steerability and polite interruption experience, confirm that:

* [ ] Users can send new messages and access control buttons while the agent is mid-run.
* [ ] The agent promptly acknowledges interruptions and restates the updated intent or constraints.
* [ ] Plans are versioned so that changes are visible and reversible where possible.
* [ ] High-stakes tasks require confirmation before executing under a revised plan.
* [ ] Safety and policy checks remain enforced even after redirections.
* [ ] Interruptions are fully logged with their impact on the plan and external systems.
* [ ] The experience is accessible via keyboard and screen readers, with clear status announcements.
